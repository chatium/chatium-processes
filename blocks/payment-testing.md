# Проверка оплаты: CRM → Pay sandbox → результат процесса

`pay:sandbox` выполняет настоящую цепочку попытки, платежа, callbacks и хуков
без списания денег и фискальных чеков. Он **не изолирует** сообщения,
автоматизации и выдачу продукта. Сначала выбери явно разрешённый тестовый
аккаунт и тестовые данные, проверь все побочные эффекты. Одна Git-ветка
не отделяет данные от боевых.

## Подготовка провайдера

Через серверный `chatium exec`/SDK в выбранном аккаунте вызови
`getAllPaymentProviders(ctx)` из `@pay/sdk`. В пустом аккаунте вызов создаёт
sandbox и возвращает реальный ID в `configured` с `isTest: true`.
`findPaymentProviders` может его не показать: по умолчанию sandbox скрыт.
Если уже есть другие провайдеры и sandbox отсутствует, используй
`ensureSandboxProvider(ctx)` из `@pay/sdk`; проверь наличие метода в
установленных типах. Если метода нет, нужен поддерживаемый выпуск Pay либо
добавление через его административный интерфейс. Не создавай строки
плагина через Heap и не пробуй боевого провайдера вместо тестового.

Сохрани ID тестового провайдера. `ensureSandboxProvider` сохраняет существующие
настройки и не меняет боевого провайдера по умолчанию. Получение ID само по
себе **не выбирает** его на странице CRM.

## Выбор безопасного пути

- Для штатной страницы CRM используй отдельный тестовый аккаунт, в котором
  единственный активный провайдер — полученный `pay:sandbox`. CRM может
  передать выбор провайдеру по умолчанию; наличие рядом боевого провайдера
  делает такой тест небезопасным. Не переключай глобальный default и не
  включай sandbox в покупательских списках рабочего аккаунта ради прогона.
- В смешанном аккаунте запуск допускается лишь через фактически доступный
  CRM-контракт с явным выбором проверенного sandbox и изоляцией эффектов.
  У текущей публичной страницы параметр `providerId` не является таким
  контрактом: не придумывай URL-параметр и не обходи CRM прямым Pay SDK.
- Проверь `getProcessTestCapabilities`. Установленный Start может не иметь
  защищённой операции оплаты; `crm.createDeal` проверяет создание сделки,
  а не полный платёж. Не выдумывай `pay.*` capabilities и не объявляй обычный
  sandbox-вызов из `process.call` изолированным TestContext.
- Полный проход штатных страниц на разрешённом отдельном стенде — самостоятельный
  браузерный сценарий `kind: browser` по [test-records](../formats/test-records.md).
  Запиши реальные ID и серверные наблюдения. Он не заменяет обязательный
  runtime-case другого контракта: неподдержанный автоматический сценарий
  остаётся blocked с причиной.

## Что пройти

1. Создай заказ **обычным обработчиком процесса** через CRM с устойчивым
   ключом, предметом/составом, тестовыми контактами и callback. Повтори
   обращение: должен вернуться тот же заказ. Не выставляй `paid` вручную.
2. Открой `/app/crm/pay?deal=<id>` и запусти предложенный способ. Перед любым
   действием на форме Pay проверь ID попытки, её `dealId`, провайдера и
   `paymentOrigin: test`. Серверные данные читай через поддерживаемый SDK,
   не верь только заголовку страницы. Если это не sandbox — остановись.
   Страница sandbox требует входа; нужны тестовый пользователь/администратор
   и штатный CSRF формы. Не подделывай callback или платёжный статус.
3. Для успеха проверь платёж `origin: test`, актуальные `getDeal`:
   `paymentStatus`, `paidTest`, неизменный `paidMoney`. Дождись callback
   и проверь фактическую выдачу результата, сообщение и остановку серии.
   Сообщение «успех» в браузере не доказывает завершение фоновых действий.
4. Ошибка и отмена не выдают результат. Для следующего пути создай новую
   попытку штатной страницей CRM; завершённую попытку не переиспользуй.
5. Если предусмотрены транши — внеси часть, проверь `partial`, затем остаток
   и одну выдачу. Повтор формы/уведомления не создаёт второй транш или доступ.
   При изменении заказа проверь актуальный остаток и повторное открытие ссылки.
6. Для возврата используй интерфейс/SDK возврата Pay на тестовом платеже;
   проверь его состояние, пересчёт CRM и предусмотренное изменение доступа.
   Сохранение карты и регулярное списание проверяй только если они нужны:
   CRM может не показывать скрытый sandbox при подборе карт. Это ограничение
   записывается явно, не обходится боевой картой или глобальной настройкой.
7. Отдельно проверь чужой заказ, чужую оплату, повторный заказ того же клиента
   и фильтрацию общих событий CRM по принадлежности процессу.

## Доказательства и завершение

В плане зафиксируй стенд, версию исходников, сценарии, допустимые эффекты и
очистку. В результате — ID сделки/попытки/платежа, значения до/после,
результат callback, выдачи и доставки, наблюдаемые ошибки и ограничения.
Токены, контакты и секретные ссылки не сохраняй в открытый отчёт.
После прогона останови свои ожидающие действия и архивируй тестовые заказы
через CRM. Сохраняй историю оплаты; провайдера и чужие записи не удаляй.
Убедись, что после очистки не осталось запланированных отправок стенда.

Этот прогон подтверждает интеграцию CRM/Pay/процесса. Он не проверяет банк,
денежный возврат, фискальную кассу и внешнюю доставку, которые не участвовали.
