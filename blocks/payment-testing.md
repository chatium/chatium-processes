# Проверка оплаты: CRM → Pay sandbox → результат процесса

Проверяй оплату в текущем аккаунте на явно выбранных тестовых заказах и своих
тестовых контактах. Наличие боевого провайдера этому не мешает. Не создавай
другой аккаунт и не переноси воронку ради подключения sandbox.

`pay:sandbox` выполняет настоящую цепочку попытки, платежа, callbacks и хуков
без списания денег и фискальных чеков. Он **не изолирует** сообщения,
автоматизации и выдачу продукта. Проверь получателей и все побочные эффекты;
Git-ветка сама по себе не отделяет данные от боевых.

## Подготовка и запуск

Агент может сам создать или получить тестового провайдера в любой момент.
Если Pay не установлен, установи его штатным SDK установки плагинов из
`chatium-development`. Выполни серверный `chatium exec --write`:

```ts
import { ensureSandboxProvider } from '@pay/sdk'
const sandbox = await ensureSandboxProvider(ctx)
```

Результат: `id`, `key: 'pay:sandbox'`, `isTest: true`, `isDefault`,
`visibleInProviderLists`, `created`. Повтор не создаёт дубль. Метод работает
и рядом с боевыми провайдерами, сохраняет существующие настройки и default.
Sandbox первоначально скрыт; `findPaymentProviders` может его не показать.
`getAllPaymentProviders` автоматически создаёт его лишь в пустом аккаунте;
для явной подготовки всегда используй `ensureSandboxProvider`.

Для выбранного тестового заказа вызови **CRM**, войдя как Admin/Developer:

```ts
import { startDealSandboxPayment } from '@crm/sdk'
const result = await startDealSandboxPayment(ctx, { dealId: testOrderId })
if (!result.success) throw new Error(result.reason)
// Открой result.link; result.providerId — sandbox для этой попытки.
```

CRM сама обеспечивает наличие sandbox, передаёт его ID явно, рассчитывает
остаток и сохраняет штатные callbacks/учёт заказа. Предварительный вызов Pay
нужен лишь для отдельной подготовки/диагностики. Отдельный аккаунт не требуется.
Ошибки не переключают попытку на боевого провайдера. Не меняй глобальный default,
не включай sandbox в покупательские списки и не обходи CRM прямым Pay SDK.

Обычная `/app/crm/pay?deal=<id>` продолжает показывать штатные способы оплаты:
создание sandbox этого не меняет. Не придумывай query `providerId` или публичный
флажок тестовой оплаты. SDK выдаёт отдельную ссылку на форму sandbox, а не
перенастраивает покупательскую страницу. Её отображение проверяется отдельно.
После отмены/ошибки новую тестовую попытку запускай тем же CRM SDK.
Каждый вызов создаёт попытку; после неопределённого ответа сначала сверь попытки
по `dealId`, затем решай, нужен ли повтор.

Если экспорт не найден, обнови typings, проверь установку/версию плагина и
фактический вызов. Зафиксируй точный отсутствующий метод или право, блокируй
только зависимую проверку. Не заменяй её реальным платежом даже на 1–10 ₽.
Другие проверки продолжай. Отдельный стенд возможен как осознанный выбор
владельца для изоляции эффектов, но не как условие подключения sandbox.

`startDealSandboxPayment` — серверный SDK для администратора/разработчика;
не оборачивай его общедоступным роутом. В обработчике выдачи разрешай `paidTest`
только для сервером выделенных тестовых заказов и получателей. Не отключай
проверку настоящей оплаты для всех клиентов и не считай `paidTest` выручкой.
Если обработчик принимает только реальные деньги, добавь ограниченный тестовый
путь для этих заказов; реальное списание для обхода проверки запрещено.

## Границы доказательства

Проверь `getProcessTestCapabilities`. Если защищённого адаптера Pay нет,
не выдумывай `pay.*` и не объявляй обычный sandbox из `process.call` изолированным
TestContext. `crm.createDeal` проверяет создание сделки, а не оплату.
Защищённый сценарий без адаптера остаётся blocked; интеграцию CRM → sandbox →
CRM → результат проверяй отдельным браузерным сценарием `kind: browser` по
[test-records](../formats/test-records.md), с реальными ID и серверными
наблюдениями. Это не требует отдельного аккаунта и не заменяет runtime-case
другого контракта.

## Что пройти

1. Создай заказ **обычным обработчиком процесса** через CRM с устойчивым
   ключом, предметом/составом, тестовыми контактами и callback. Повтори
   обращение: должен вернуться тот же заказ. Не выставляй `paid` вручную.
2. Вызови `startDealSandboxPayment` для этого заказа и открой `result.link`. Перед любым
   действием на форме Pay проверь ID попытки, её `dealId`, провайдера и
   `paymentOrigin: test`. Серверные данные читай через поддерживаемый SDK,
   не верь только заголовку страницы. Если это не sandbox — остановись.
   Страница sandbox требует входа; нужны тестовый пользователь/администратор
   и штатный CSRF формы. Не подделывай callback или платёжный статус.
3. Для успеха проверь платёж `origin: test`, актуальные `getDeal`:
   `paymentStatus`, `paidTest`, неизменный `paidMoney`. Дождись callback
   и проверь фактическую выдачу результата, сообщение и остановку серии.
   Сообщение «успех» в браузере не доказывает завершение фоновых действий.
4. Ошибка и отмена не выдают результат. Для следующего пути создай новую
   попытку через `startDealSandboxPayment`; завершённую попытку не переиспользуй.
5. Если предусмотрены транши — внеси часть, проверь `partial`, затем остаток
   и одну выдачу. Повтор формы/уведомления не создаёт второй транш или доступ.
   При изменении заказа проверь актуальный остаток и повторное открытие ссылки.
6. Для возврата используй интерфейс/SDK возврата Pay на тестовом платеже;
   проверь его состояние, пересчёт CRM и предусмотренное изменение доступа.
   Сохранение карты и регулярное списание проверяй только если они нужны:
   CRM может не показывать скрытый sandbox при подборе карт. Это ограничение
   записывается явно, не обходится боевой картой или глобальной настройкой.
7. Отдельно проверь чужой заказ, чужую оплату, повторный заказ того же клиента
   и фильтрацию общих событий CRM по принадлежности процессу.

## Доказательства и завершение

В плане зафиксируй стенд, версию исходников, сценарии, допустимые эффекты и
очистку. В результате — ID сделки/попытки/платежа, значения до/после,
результат callback, выдачи и доставки, наблюдаемые ошибки и ограничения.
Токены, контакты и секретные ссылки не сохраняй в открытый отчёт.
После прогона останови свои ожидающие действия и архивируй тестовые заказы
через CRM. Сохраняй историю оплаты; провайдера и чужие записи не удаляй.
Убедись, что после очистки не осталось запланированных отправок стенда.

Этот прогон подтверждает интеграцию CRM/Pay/процесса. Он не проверяет банк,
денежный возврат, фискальную кассу и внешнюю доставку, которые не участвовали.
