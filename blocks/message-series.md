# Компонент: серия сообщений

**Для бизнеса.** Подтверждения, прогрев, напоминания и дожим в почте и
мессенджерах. Одна серия — одна цель, например довести до оплаты.

## Контракт

- Письма — `.mailings/storage/processes/<process>/<series>/*.message.yaml`.
  Формат — [letters.md](../formats/letters.md).
- Отправка из кода — `sendMessageFromTemplate` из `@mailings/sdk`.
  Для чтения в серверном коде — `readMessageFile` из того же SDK. Для правки
  файлов агент пользуется своими инструментами. Не создавай читателей
  через `app.function`, не копируй парсер YAML и отправку Sender в процесс.
- Задержки и условия — шаги [автоматизации](automation.md). В карте серия
  обозначается `kind: series`, `source` — папка писем.

## Действие сообщения

Когда для сообщения нужно получить клиента по заявке/заказу, подготовить
ссылку, дату, сумму или проверить бизнес-условие, создай действие этого
сообщения. Внутри оно готовит `contacts` и `variables`, затем вызывает SDK
Mailings и обрабатывает результат. Это обычный вариант, не исключение.
Не добавляй отдельный шаг подготовки только ради вызова общего экшена.
Выделяй подготовку в отдельный шаг, когда её результат действительно нужен
нескольким следующим шагам или она имеет самостоятельный смысл в процессе.

Действие находится в `automations/<automation>/actions/`; общие для нескольких
автоматизаций действия — в `<process>/actions/`. Зарегистрируй их через
`app.accountHook('@automations/actions', ...)` по справке
`chatium-development/references/automations/actions.md`.
`scaffold` не создаёт отправитель или регистрацию заранее.

В конфиге шага явно укажи `messageKey`: ключ относительно `.mailings/storage/`,
без расширения, например `processes/shop-orders/order/01-confirmation`.
Действие принимает этот параметр и передаёт SDK; так `check` и карта видят
связь шага с письмом. Другие параметры описывают нужную бизнес-сущность:

```json
{
  "messageKey": "processes/shop-orders/order/01-confirmation",
  "orderId": { "$ref": "event.orderId" }
}
```

Источник получателя определи явно: контакты события, контакты из параметров
или клиент указанного заказа/заявки. Отсутствие контактов в событии допустимо,
но действие не должно отправлять сообщение, пока получатель не определён.
Не считай email единственным типом контакта. Подготовка бизнес-данных остаётся
в действии; выбор смежных контактов через CRM, их приоритет и правила доставки
по каналам относятся к Sender. Через SDK Mailings можно передать
`expandCustomerContacts: true`: Sender определит одного клиента CRM и добавит
только уникальные контакты отсутствующих типов для выбранных каналов. Явно
переданный email не заменяется и не дополняется другими почтами. Несколько
адресов нового типа пропускаются с `AMBIGUOUS_CONTACT_TYPE` в `warnings`;
нужный адрес передаётся явно. Без флага прежний список контактов сохраняется.
Если CRM недоступна, клиент не найден или неоднозначен либо превышен лимит,
Sender пропускает расширение с предупреждением и отправляет на исходные контакты.
Проверь поддержку параметра в установленном SDK по
`chatium-development/references/sender/messaging.md`; не копируй правила в процесс.

## Когда подходит общий экшен

Если получатель и переменные уже готовы и дополнительной бизнес-логики нет,
можно использовать подходящее общее действие из реестра аккаунта. Проверь
наличие и схему через `getAutomationActions` из `@automations/sdk`; не считай
какое-либо имя общего экшена обязательным или гарантированно доступным.
Отсутствие общего экшена не мешает действию сообщения вызывать доступный SDK
Mailings. Если нужного метода SDK нет, сообщи о недостающей версии плагина;
не заменяй его копией чтения шаблонов и доставки.

Контракт параметров берётся из реестра. В варианте с `var_<name>` это плоские
параметры: Automations раскрывает `$ref` и `$template` на верхнем уровне
`params`, но не внутри вложенного объекта. Ссылкой можно передать целый
готовый объект/массив из события или предыдущего шага, если его принимает
схема действия. Параметр `email`, если он есть в установленной версии,
не является универсальным механизмом адресации.

`actionRoute.routeJson` общего экшена получает ID **плагина**, отличающийся
от accountId процесса. Для `check --registry FILE` сохрани JSON реестра вне
репозитория: `{accountId, actions: [{routeJson, inputSchema}], conditions: []}`.
`accountId` — целевой аккаунт, `inputSchema` — массив `{name, required}`
из схемы `body.params`. Полный контракт —
`chatium-development/references/automations/registry.md`. Без реестра внешний
маршрут не считается проверенным. После смены версии плагина обнови реестр.

## Настройки и тестовые отправки

Для ключей `processes/<process>/...` SDK определяет процесс по ключу и
читает его `.workspace.json → config`:

```json
{
  "senderChannels": [],
  "mailings": {
    "testOnly": true,
    "testContacts": [{"type": "email", "value": "owner+test@example.com"}]
  }
}
```

Агент обязан заполнить `senderChannels` ID выбранных каналов по
[правилам настройки](channels.md). Если каналы ещё не подключены, оставь
пункт «Нужно от вас» и продолжай сборку: `check` выдаёт предупреждение,
не блокер. Перед тестовой отправкой каналы должны быть выбраны и проверены.
SDK Mailings для шаблона процесса отклоняет фактическую отправку без выбранных
каналов. В новых шаблонах укажи `processDeliveryChannelIds` по
`channelIdsByFormat` из задания: Mailings ограничит ими доставку.
Явный `channels` вызова может только сузить этот список и
`config.senderChannels`. У старых шаблонов без нового поля сохраняется
прежний выбор каналов из вызова или настроек процесса.
Сам Sender по-прежнему трактует пустой список каналов как отсутствие ограничения;
не обходи проверку процесса прямым вызовом Sender.

До согласованного запуска `testOnly: true`. SDK отклоняет **всю отправку**,
если хотя бы одного исходного получателя нет в `testContacts`. Отсутствие настроек тоже
блокирует отправку. `scaffold` создаёт пустой список тестовых контактов,
агент заполняет его разрешёнными контактами. На запуске после согласия —
`testOnly: false`. `analyticsMode: 'test'` сам по себе не ограничивает доставку.
Mailings сверяет явно переданные контакты с `testContacts` до вызова Sender.
Пока `testOnly: true`, `expandCustomerContacts: true` запрещён: CRM могла бы
добавить реальные контакты. После согласованного запуска расширение можно
включить вместе с `testOnly: false`.

Переменные в коде передаются SDK в `variables`; SDK проверяет обязательные
переменные выбранного варианта до отправки и сохраняет медиа, вложения и кнопки.
Варианты `<key>.vN.message.yaml` выбираются SDK с учётом `segment`; даже ключ
с `.vN` не закрепляет конкретный вариант. Для фиксированного письма используй
отдельный ключ без альтернатив. Аналитика: `originType: mailings-template`,
`originId` — относительный путь выбранного варианта.

## Проверка и показ

- `check` проверяет шаблон и все варианты, декларации переменных, ссылки
  шагов, тестовый режим, настройку каналов и внешний маршрут по реестру.
  Для общего экшена сверяет `var_<name>`. Для локального действия не требует
  их в параметрах: значения могут вычисляться внутри; предупреждение
  напоминает проверить получателя и переменные при ревью кода и тестовом
  вызове. Это статическая проверка, не подтверждение доставки.
- Тестовый вызов — через SDK с разрешённым контактом. Проверяй `success`,
  `error`, `variantUsed` и `channelResults`. Успешный общий результат
  не означает доставку всем получателям. `sentTo` общего экшена, если есть,
  считает переданные контакты, а не подтверждённые доставки.
- На запуске заполни `tests/message-delivery.json` по
  [формату тестового прогона](../formats/test-records.md). `check` требует
  успешный `channelResults` для каждого ID, каждого шаблона и варианта,
  включая серии с ручным вызовом; обещанное медиа нужно открыть и отметить.
- Дедупликации в SDK нет: не включай автоматический повтор шага отправки.
  Возврат `success: false` Automations сохраняет как предупреждение, поэтому
  учитывай результат в дальнейшей логике и проверь журнал выполнения.
- После правки покажи письмо в Mailings по `chatium-development/preview.md`.
  Путь превью включает `.message.yaml`. В финале открой карту процесса.

## Переход существующего процесса

Установка скилла не удаляет старые функции и не меняет маршруты действующих
автоматизаций. При согласованном переходе проверь доступность SDK, перенеси
TEST_ONLY/TEST_CONTACTS в `config.mailings`, замени `letterPath` на `messageKey`
и внутреннюю отправку на вызов SDK. Сохрани подготовку контактов, переменных
и бизнес-проверки в действии; общий экшен не является целью миграции.
Проверь потребителей во всём аккаунте и тестовую отправку до удаления
неиспользуемых помощников. Для старого поколения процессов сначала применяй
[режим совместимости](../build/legacy-processes.md).
