# Кубик: серия сообщений

**Для бизнеса.** Письма и сообщения в мессенджерах, которые клиент
получает по ходу процесса: подтверждение, прогрев, напоминания, дожим.

**Когда брать.** Клиенту нужно что-то сказать после события или по времени.
Одна серия — одна цель («довести до оплаты заказа»).

Как Sender отправляет и подбирает каналы — `chatium-development`,
`references/sender/messaging.md`.

## Контракт

- **Письма** — файлы в `.mailings/storage/processes/<process>/<series>/`,
  формат — [letters.md](../formats/letters.md).
- **Отправка** — шаг автоматизации с действием «письмо по пути». Пока
  общего действия в Sender нет, в процессе живёт временный хелпер
  `<process>/actions/send-letter.ts` (кладёт `scaffold`). Не переписывай
  его под конкретное письмо.
- **Чтение письма.** `readWorkspaceFile` видит только воркспейс
  вызывающего модуля, а письма лежат в отдельном воркспейсе хранилища.
  Поэтому хелпер зовёт `readLetterFn` из `.mailings/storage/read-letter.ts`
  — один читатель на аккаунт, его кладёт `scaffold`. Правка письма в
  редакторе доходит до рантайма с публикацией, без пересборок.
- **Задержки и условия** — шаги автоматизации, не поля письма
  ([automation.md](automation.md)).
- В карте — узел `kind: series`, `source` — папка серии.

## Параметры шага отправки

Параметры плоские: рантайм автоматизаций не разбирает вложенные объекты.

| Параметр | Что это |
| --- | --- |
| `letterPath` | Путь письма от корня аккаунта, строкой |
| `email` | По желанию: адрес получателя. Без него — контакты клиента из события |
| `var_<name>` | Значение переменной `{{name}}` письма |

Пример — подтверждение заказа в интернет-магазине (процесс `shop-orders`):

```json
{
  "type": "action",
  "id": "send_confirmation",
  "actionName": "Письмо «Заказ принят»",
  "actionRoute": {
    "routeType": "function",
    "routeJson": [12345, "shop-orders/actions/send-letter", "/send-letter"]
  },
  "params": {
    "letterPath": ".mailings/storage/processes/shop-orders/order/01-confirmation.message.yaml",
    "var_name": { "$ref": "event.name" },
    "var_order_total": { "$ref": "steps.prepare.orderTotal" },
    "var_payment_url": { "$ref": "steps.prepare.paymentUrl" }
  }
}
```

## Откуда берутся переменные

- **Из события** — `$ref: event.<поле>`, поле объявлено в `payloadMapping`.
- **Из шага подготовки** — `$ref: steps.<id>.<поле>`: действие процесса
  считает значения (платёжная ссылка, адрес, дата из настроек) и
  возвращает их в `result`, ничего не отправляя. Одно действие подготовки
  обслуживает несколько писем.
- **Константа** — строка прямо в параметре или `$template`:
  `{ "$template": "Здравствуйте, {{ event.name }}" }`.

## Как проверить

- `check`: письмо по `letterPath` существует; каждая переменная из
  `variables` письма приходит параметром `var_<name>`; каждый `$ref` ведёт
  на поле события или на шаг выше; каждое письмо серии кто-то отправляет.
- Smoke через `chatium exec`: вызвать `sendLetter` из хелпера с теми же
  параметрами, что у шага, и тестовым контактом. В `result` — путь письма
  и число получателей; доставку видно в `findMessagesByChatId`.

## Грабли

- Sender молча заменяет пустые `{{…}}` на пустую строку. Поэтому хелпер не
  шлёт письмо без обязательной переменной, а `check` сверяет переменные.
- Хелпер при `TEST_ONLY = true` в `tests/records.ts` шлёт только на
  тестовые контакты — остальных пропускает с сообщением в `result`.
- Повторной отправки при ретрае автоматизации хелпер пока не защищает.
  Ставь `settings.continueOnError: true` и не делай ретраи шагов отправки.
- Каналы берутся из `config.senderChannels` процесса. Пусто — Sender
  выберет каналы сам по типу контакта. Для SMS у письма нужен `short`.
- В аналитике отправки хелпер помечает `originType: funnel`,
  `originId: <process>:<путь письма>`.
