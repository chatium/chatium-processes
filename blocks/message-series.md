# Компонент: серия сообщений

**Для бизнеса.** Подтверждения, прогрев, напоминания и дожим в почте и
мессенджерах. Одна серия — одна цель, например довести до оплаты.

## Контракт

- Письма — `.mailings/storage/processes/<process>/<series>/*.message.yaml`.
  Формат — [letters.md](../formats/letters.md).
- Отправка из кода — `sendMessageFromTemplate` из `@mailings/sdk`.
  Для чтения в серверном коде — `readMessageFile` из того же SDK. Для правки
  файлов агент пользуется своими инструментами. Не создавай читателей
  через `app.function`, не копируй парсер YAML и отправку Sender в процесс.
- В автоматизации используй общее действие Mailings `mailingsSendTemplate`.
  Перед сборкой проверь наличие действия и его схему в реестре целевого
  аккаунта через `getAutomationActions` из `@automations/sdk`. Если действия
  ещё нет, сообщи о недостающей версии плагина; не подменяй его копией.
- Задержки и условия — шаги [автоматизации](automation.md). В карте серия
  обозначается `kind: series`, `source` — папка писем.

## Параметры общего действия

Параметры плоские: Automations не раскрывает вложенные `$ref` и `$template`.

| Параметр | Значение |
| --- | --- |
| `messageKey` | Ключ относительно `.mailings/storage/`, без расширения: `processes/shop-orders/order/01-confirmation` |
| `email` | Необязательный адрес; если не передан, используются `context.customerContacts` события |
| `segment` | Необязательный сегмент для выбора варианта шаблона |
| `var_<name>` | Значение переменной письма `{{name}}` |

Пример **params**, маршрут берётся из реестра, а не из примера:

```json
{
  "messageKey": "processes/shop-orders/order/01-confirmation",
  "var_name": { "$ref": "event.name" },
  "var_payment_url": { "$ref": "steps.prepare.paymentUrl" }
}
```

`actionRoute.routeJson` получает ID **плагина**, он отличается от accountId
процесса. Для проверки `check --registry FILE` сохрани JSON реестра вне
репозитория: `{accountId, actions: [{routeJson, inputSchema}], conditions: []}`.
`accountId` — целевой аккаунт, `inputSchema` — массив `{name, required}`
из схемы `body.params`. Полный контракт получения реестра —
`chatium-development/references/automations/registry.md`; установленный
SDK и реестр имеют приоритет перед справкой. Без реестра внешний маршрут
не считается проверенным. После изменения версии плагина обнови реестр.

## Настройки и тестовые отправки

Для ключей `processes/<process>/...` SDK определяет процесс по ключу и
читает его `.workspace.json → config`:

```json
{
  "senderChannels": [],
  "mailings": {
    "testOnly": true,
    "testContacts": [{"type": "email", "value": "owner+test@example.com"}]
  }
}
```

До согласованного запуска `testOnly: true`. SDK отклоняет **всю отправку**,
если хотя бы одного получателя нет в testContacts. Отсутствие настроек тоже
блокирует отправку. `scaffold` создаёт пустой список, его заполняет агент
разрешёнными контактами. На запуске после согласия — `testOnly: false`.
`analyticsMode: 'test'` сам по себе не ограничивает доставку.

Каналы берутся из `config.senderChannels`; если пусто — из явного `channels`
SDK, затем из шаблона, иначе их выбирает Sender. Переменные в коде передаются
в `variables`, в общем действии — через `var_<name>`. SDK проверяет обязательные
переменные выбранного варианта до отправки и сохраняет медиа, вложения и кнопки.
Варианты `<key>.vN.message.yaml` выбираются SDK с учётом `segment`; даже ключ
с `.vN` не закрепляет конкретный вариант. Для фиксированного письма используй
отдельный ключ без альтернатив. Аналитика: `originType: mailings-template`,
`originId` — относительный путь выбранного варианта.

## Особая логика процесса

Для вычисления платёжной ссылки, даты или суммы создай отдельное действие
подготовки. Оно возвращает данные для следующего общего шага отправки.
Наличие разных писем не требует разных обработчиков.

Своя обёртка оправдана, когда нужна отдельная бизнес-операция: проверка допуска,
учёт отправки, получение адресата или защита от повторов. Опиши её назначение
в плане, внутри вызывай SDK Mailings и зарегистрируй только это действие через
`app.accountHook('@automations/actions', ...)`. `scaffold` не создаёт обёртку
или регистрацию заранее. Не переписывай выбор шаблона и доставку самостоятельно.

## Проверка и показ

- `check` проверяет существование шаблона и всех вариантов, объявленные
  переменные, ссылки шагов, настройки тестового режима и внешний маршрут
  по переданному реестру. Это статическая проверка, не подтверждение доставки.
- Тестовый вызов — через SDK с разрешённым контактом. Проверяй `success`,
  `error`, `variantUsed` и `channelResults`. Общее действие возвращает
  `{success, result}`; успешный `result` содержит `filePath`, `variantNumber`,
  `sentTo`. Это число переданных контактов, не подтверждённых доставок.
- Дедупликации в SDK нет: не включай автоматический повтор шага отправки.
  Возврат `success: false` Automations сохраняет как предупреждение, поэтому
  учитывай результат в дальнейшей логике и проверь журнал выполнения.
- После правки покажи письмо в Mailings по `chatium-development/preview.md`.
  Путь превью включает `.message.yaml`. В финале открой карту процесса.

## Переход существующего процесса

Установка скилла не удаляет старые функции и не меняет маршруты действующих
автоматизаций. При согласованном переходе сначала проверь доступность общего
действия и SDK, перенеси TEST_ONLY/TEST_CONTACTS в config.mailings, замени
letterPath на messageKey и маршрут на значение из реестра. Проверь вызовы
и тестовую отправку. Удаляй прежние send-letter/read-letter и регистрацию
только после отсутствия потребителей во всём аккаунте. Для старого поколения
процессов сначала применяй [режим совместимости](../build/legacy-processes.md).
