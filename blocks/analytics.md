# Аналитика пути клиента

Начни с вопроса владельца: что он будет решать по отчёту. Затем определи
реальные события из `specs/events.yaml`, их писателей и доступные поля. Для
каждой заявленной цели отличай измеренный результат от удобного косвенного
показателя: число отправленных уроков не доказывает, что человек их прошёл
или составил план. Если результат не наблюдается, честно назови метрику
доставки и способ отдельно проверить обещанный итог. Для конверсии нельзя
просто поделить число оплат на число просмотров: события
должны относиться к одной идентичности, идти по времени и находиться в
объявленном окне. Просмотр без связи с клиентом не становится клиентским
шагом от соседства с заявкой. Если способ связывания не реализован,
сформулируй ограничение и не называй расчёт воронкой клиентов.
Для каждой доли отдельно зафиксируй числитель, знаменатель, единицу
подсчёта (клиент, заявка или заказ), период и судьбу ожидающих и повторных
исходов. Сверь это определение с планом владельца. `steps[0]` в воронке
задаёт исходную когорту: `[request_created, request_confirmed]` отвечает
на вопрос о подтверждении среди всех начавших путь, а не среди заявок с
решением. Единица подсчёта зависит от `identity`.

Когда процесс обещает собственную воронку, создай
`<process>/specs/analytics.yaml`:

```yaml
funnels:
  - id: lead_to_payment
    question: Какая доля клиентов с заявкой оплатила заказ за 30 дней?
    identity: customer
    windowDays: 30
    steps: [lead_created, order_paid]
    deduplicateBy: orderId
```

`steps` — ключи объявленных `customerEvent`, в порядке пути клиента.
`windowDays` — время от первого до последнего шага. Если есть событие
категории `revenue`, `deduplicateBy` ссылается на поле заказа из его
`payloadMapping`, чтобы повторный callback не считался второй оплатой.
`identity: customer` считает клиентов: повторные заявки одного клиента не
становятся двумя заявками. Для подсчёта заявок или заказов укажи
`identity: entity` и `identityField: requestId` (или другой строковый ключ),
который передаётся в `payloadMapping` каждого шага. Ревьюер проверяет,
что код действительно пишет один и тот же ID, а не только одинаковое имя
поля в спецификации.

Долю одного исхода среди уже решённых описывай отдельным отношением:

```yaml
ratios:
  - id: confirmation_among_decided
    question: Какая доля заявок с решением подтверждена за 30 дней?
    numeratorEvent: request_confirmed
    denominatorEvents: [request_confirmed, request_refused]
    subjectField: requestId
    periodDays: 30
    conflictRule: exclude-and-report
```

Знаменатель — число разных `requestId`, по которым в периоде есть хотя бы
одно из `denominatorEvents`; числитель — число этих же `requestId` с
`numeratorEvent`. Ожидающие решения не входят в знаменатель и показываются
отдельно. Повтор исхода не увеличивает счётчик. Если одна заявка получила
взаимоисключающие исходы, исключи её из обоих счётчиков и покажи ошибку
данных для разбора; не выбирай исход по порядку событий молча.
Не копируй рекламные расходы или телеметрию Mailings в локальную таблицу.
Для простой метрики из одного события вместо `funnels` допустим
`metrics: [{id: lead_count, question: "Сколько заявок?", sourceEvents: [lead_created]}]`.
Связанный путь описывай в `funnels`, долю взаимоисключающих исходов — в
`ratios`; не дели несвязанные счётчики. Если код вызывает `queryAi`, файл обязателен даже для
одной метрики.
Историческую аналитику читай штатным способом ClickHouse, с ограниченным
периодом и объёмом результата; проверь контракт в `chatium-development`.
Для разового `chatium exec` бери точные URL **объявленных** событий из
`getAccountEvents(ctx)` и сверяй их с ключами `specs/events.yaml` и путём
процесса. Вызов `getCustomerEventUrl(ctx, key)` прямо из сниппета может не
получить контекст исходного файла и вернуть общий URL без пути процесса;
такой запрос молча пропустит нужные события. По той же причине вызов
`route.run(ctx, …)` через `chatium exec` не подтверждает URL события,
который запишет настоящий HTTP-маршрут: проверяй событие после вызова
опубликованной формы или маршрута. Не подбирай URL поиском по всем
логам. Если журнал недоступен, показывай локальный расчёт лишь как прокси:
признак полной проверки должен оставаться ложным до независимой сверки.
После тестового события дополнительно сверь его фактический `urlPath` по
известному ID записи с объявленным URL. Успешный ответ CRM и наличие события
в реестре по отдельности не доказывают совпадения. Если журнал показывает
общий URL без пути процесса, не считай ни воронку, ни подписку проверенными:
исправь SDK, перестрой аккаунт-потребитель и повтори ограниченный тест.

`check` проверяет существование событий, тип и объявленный ключ идентичности,
поле дедупликации и состав отношения. Он не доказывает, что запрос действительно связывает события
одного клиента, упорядочивает их по времени, применяет окно и корректно
считает когорты. Эти пункты и реальные результаты проверяет ревьюер и
тестовый прогон. Для `identity: entity` дополнительно проверь, что каждый
писатель действительно передаёт один и тот же ID сущности.
