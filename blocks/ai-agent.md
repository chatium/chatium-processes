# Самостоятельный помощник в процессе

**Назначение.** Ведёт согласованную часть пути клиента или помогает сотруднику, когда для задачи нужны понимание свободного текста и выбор ответа по контексту. Для однозначной операции используй обычную автоматизацию.

**Контракт.** Каждый самостоятельный агент — отдельный `<process>/agents/<key>.agent.json` и узел `kind: agent` в `process.yaml`. Связи и требования описаны в `agents/spec.yaml`, испытания — в `agents/cases.yaml`; точный формат — [formats/agents.md](../formats/agents.md). Не создавай отдел, supervisor или inline-специалистов. Конфиг в Source Git редактируется как файл, затем публикуется обычным способом. Платформенный ID выясняй после публикации, впиши его в `agentId` узла и обнови снимок карты; не выводи ID из имени файла.

**Знания и действия.** Общие факты хранятся в базе знаний, но ссылку в спецификации нельзя считать доступом агента. Проверь, чем именно нужные знания попадают в его контекст. Подключай только необходимые инструменты; для каждого выясни разрешения, бизнес-параметры, побочный эффект, повтор и способ остановки. Динамические цены, статусы и наличие получай из источника в момент действия. Инструкции составь по [смысловому стандарту](../build/agent-instructions.md): цель, границы, ход разговора, примеры, ошибка и передача человеку; одних заголовков и объёма текста недостаточно.

**Вход и передача.** Для общего канала определи первого адресата, продолжение существующей цепочки, fallback и условия переключения. При передаче другому агенту явно задай разрешённую цель, короткое резюме, сохраняемый серверный контекст и действие при сбое. CRM-связь, память и остановку старых касаний проверь фактически; текстовое резюме само по себе их не переносит. Настройка канала и цепочки может быть общей для веток — не меняй её как изолированный preview.

**Автономность.** Укажи, что запускает инициативный контакт, часы тишины, лимиты, остановку после ответа/отказа и пересечение с автоматизациями. Прямой Sender-tool не защищён настройкой тестовых рассылок Mailings; живые испытания проводи только с проверенными тестовыми контактами и ограниченными инструментами.

**Проверка.** `check` сверяет файлы, связи и базовую структуру, но не доказывает регистрацию инструментов, маршрута и качество диалога. После публикации запусти `agents-runtime.mjs <process> --record`: он сверит исполненный коммит, ветку, SHA-256, `agentId`, инструменты и маршрут **нового обращения** через публичный SDK и запишет результат только при `verified`. Для маршрута заранее укажи собственные `testContacts` клиента в CRM без открытой цепочки; при необходимости добавь `testExistingContacts` другого тестового клиента с CRM-цепочкой. Без общего канала `routes` может быть пустым. Папка процесса до вызова должна быть без неопубликованных правок. Затем закоммить и опубликуй `tests/agents-runtime.json`; `check --task-stage test` и `launch` требуют запись, привязанную к опубликованным конфигам и текущей ветке. Для запуска повтори проверку не ранее чем за 15 минут до `check`: настройки канала могут измениться вне Git. После переноса в `main` повтори проверку там. Проверяй результат в настоящем preview-контексте: одна локальная смена ветки его не создаёт. `partial` означает, что нужны дополнительные испытания или подтверждение каталога. SDK dry-run по контактам не доказывает вход без CRM-ключа, реальную передачу и перенос контекста — пройди контролируемый сценарий и передай наблюдения [независимому ревьюеру](../build/agent-review.md). Живой эффект проверь отдельно; недоступное runtime-свойство отмечай как непроверенное.
