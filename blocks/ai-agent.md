# Самостоятельный помощник в процессе

**Назначение.** Ведёт согласованную часть пути клиента или помогает сотруднику, когда для задачи нужны понимание свободного текста и выбор ответа по контексту. Для однозначной операции используй обычную автоматизацию.

**Контракт.** Каждый самостоятельный агент — отдельный `<process>/agents/<key>.agent.json` и узел `kind: agent` в `process.yaml`. Связи и требования описаны в `agents/spec.yaml`, испытания — в `agents/cases.yaml`; точный формат — [formats/agents.md](../formats/agents.md). Не создавай отдел, supervisor или inline-специалистов. Конфиг в Source Git редактируется как файл, затем публикуется обычным способом. Платформенный ID выясняй после публикации, впиши его в `agentId` узла, опубликуй изменение и дождись автоматического обновления карты; не выводи ID из имени файла.

**Знания и действия.** Общие факты хранятся в базе знаний, но ссылку в спецификации нельзя считать доступом агента. Проверь, чем именно нужные знания попадают в его контекст. Подключай только необходимые инструменты; для каждого выясни разрешения, бизнес-параметры, побочный эффект, повтор и способ остановки. Динамические цены, статусы и наличие получай из источника в момент действия. Инструкции составь по [смысловому стандарту](../build/agent-instructions.md): цель, границы, ход разговора, примеры, ошибка и передача человеку; одних заголовков и объёма текста недостаточно.

`context.customerContacts`, `chainId` и другие поля контекста подставляет рантайм агента, но при прямом вызове `app.function` вызывающий может передать такое же тело сам. Если инструмент читает личные данные или совершает действие, сначала проверь `callerInfo` от платформы и разреши только ожидаемый плагин `agent-process`; затем проверяй принадлежность записи и текущую волю клиента. Не считай одним только `context` доказательство подлинности вызова.

Если помощник вызывает два инструмента подряд, проверь их совместимость на конкретных полях: что вернул первый и что ожидает второй. Модель выбирает бизнес-селектор, а сервер находит CRM-клиента и принадлежащую ему запись; не проси модель переносить технический ID клиента или заявки между действиями. Если у клиента несколько подходящих записей, нельзя молча брать последнюю. Для действия с побочным эффектом сервер должен проверить свежий выбор из доверенного текущего контекста; если такой проверки нет, откажи, даже когда модель передала существующий селектор из старой истории. При отсутствии, неоднозначности или старом формате ответа действие должно отказать без побочного эффекта. Добавь такие случаи в `agents/cases.yaml` и передай на профильное ревью до общего живого прогона.

Просьба модели выполнить действие не подтверждает волю клиента. Перед уведомлением сотрудника, отправкой, записью или иной операцией с побочным эффектом серверный инструмент проверяет **текущий** запрос или отдельное подтверждение человека, привязанное к этой цепочке и входящему сообщению; `reason`, флаг согласия и текст из `input` модели не служат таким подтверждением. Если SDK не даёт проверить текущий ход, используй отдельный экран/действие подтверждения либо откажи без эффекта. Отрицательный сценарий: в истории есть старая просьба, но сейчас клиент спрашивает статус или отзывает её; даже при одной принадлежащей ему записи действие не выполняется. Проверка должна быть ограниченной по объёму чтения и отказывать при недоступности истории.

**Вход и передача.** Для общего канала определи первого адресата, продолжение существующей цепочки, fallback и условия переключения. Если передача следует из достижения понятного бизнес-результата, предпочитай встроенную цель `goal.type: "redirect2"` в конфиге самостоятельного агента: задай проверяемый `trigger` и разрешённые `redirectToAgentIds`. Платформа даёт агенту `complete-goal`, а при нескольких кандидатах — `find-redirect-candidates`; вызов при подтверждённом результате передаёт цепочку и отмечает цель достигнутой. Не подменяй это словами «цель достигнута» в инструкции и не вызывай цель при сомнении или ради обработки ошибки. Старый `goal.type: "redirect"` не используй для новых ролей.

При передаче явно задай следующую роль, разрешённые факты о клиенте, серверный контекст и действие при сбое. В `agents/spec.yaml` свяжи каждый handoff с `mechanism` и сценарием `case`, проверяющим успешный и неуспешный исход. `goal.messageText` — фиксированный текст для следующей роли, он не составляет новое резюме по диалогу. Текущие факты и статус сохраняй в CRM/операционной записи; если необходимо передать индивидуальное резюме из этого разговора прямо в `messageText` либо переключение запускает серверное событие, используй проверенный серверный инструмент с публичным `redirectChain`/`redirectChainByContacts`. CRM-связь, контекст и остановку старых касаний проверь фактически; один текст не создаёт общей памяти. Настройка канала и цепочки может быть общей для веток — не меняй её как изолированный preview.

Если помощник оставляет сотруднику обращение или ссылку на него, защищённая карточка должна при открытии перечитать текущее состояние клиента. Ранее поставленное обращение не разрешает контакт после отказа или остановки; покажи сотруднику явное предупреждение. Проверь случай «обращение создано → контакт остановлен → карточка открыта» без повторной отправки. Принятие уведомления транспортом не доказывает, что сотрудник его увидел.

**Ручной вход без транспорта.** Укажи в `agents/spec.yaml` приёмник ответа: `delivery.kind: direct-output` с существующим `delivery.handler` либо проверенный `send-tool`. В первом случае передай `directOutputTool` с этой функцией в `pushMessageToChain`. Иначе модель может многократно вызывать отсутствующий `sendMessageToChat`; одного `routes: []` недостаточно. Для испытания выдели отдельный `chainKey`, предел ходов и способ остановить цепочку через `stopChain`. Сверь ответ с историей и результатом приёмника, не подключая реальную доставку ради проверки текста.

**Автономность.** Укажи, что запускает инициативный контакт, часы тишины, лимиты, остановку после ответа/отказа и пересечение с автоматизациями. Прямой Sender-tool не защищён настройкой тестовых рассылок Mailings; живые испытания проводи только с проверенными тестовыми контактами и ограниченными инструментами.

**Проверка.** `check` сверяет файлы, связи и базовую структуру, но не доказывает регистрацию инструментов, маршрута и качество диалога. После публикации запусти `agents-runtime.mjs <process> --route-tests FILE --record`: он сверит исполненный коммит, веточный отпечаток из записи хука сборки, `agentId`, инструменты и маршрут через публичный SDK и запишет результат только при `verified`. Для канала передай через `FILE` вне Git-аккаунта собственные контакты клиента в CRM без открытой цепочки и другого тестового клиента с CRM-цепочкой; формат — в [спецификации](../formats/agents.md). Без обеих проверок результат частичный. Без общего канала `routes` может быть пустым, и файл контактов не нужен. Папка процесса до вызова должна быть без неопубликованных правок. Затем закоммить и опубликуй `tests/agents-runtime.json`; `check --task-stage test` и `launch` требуют запись, привязанную к опубликованным конфигам и текущей ветке. Для запуска повтори проверку не ранее чем за 15 минут до `check`: настройки канала могут измениться вне Git. После переноса в `main` повтори проверку там. Для живого диалога используй preview-контекст нужной ветки. `partial` означает, что нужны дополнительные испытания или подтверждение каталога. SDK dry-run по контактам не доказывает вход без CRM-ключа, реальную передачу и перенос контекста — пройди контролируемый сценарий и передай наблюдения [независимому ревьюеру](../build/agent-review.md). Живой эффект проверь отдельно; недоступное runtime-свойство отмечай как непроверенное.
