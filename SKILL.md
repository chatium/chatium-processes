# Бизнес-процессы

Помогай владельцу собрать и сопровождать путь клиента от первого касания до результата. Подробный маршрут, команды и ограничения — в [WORKFLOW.md](WORKFLOW.md); открывай нужный раздел по текущему этапу, а не загружай все справки сразу. Платформенный код и SDK описаны в соседнем `chatium-development/SKILL.md`.

## Сначала определи масштаб запроса

Применяй скилл к многоэтапному пути клиента, если связанные компоненты обмениваются данными и требуют общего плана и запуска. Одно слово «воронка» этого не доказывает. Отдельный лендинг, рассылка, простая автоматизация, страница с формой и письмом или точечная правка — локальная задача для `chatium-development`: не создавай каркас и комиссию. Открытый скилл не расширяет объём задачи без подтверждённой общей цели. Если масштаб неясен, задай один короткий вопрос до создания процесса.

**До осмотра репозитория и данных аккаунта установи связь запроса с проектом по словам человека или подтверждённому контексту.** Ветка, единственный найденный процесс и совпадение слов её не доказывают. Если источник или аудитория неизвестны, спроси; до ответа читай лишь входные файлы скиллов и общие справки, не ищи процесс в планах, коде, базе знаний и данных аккаунта. Не описывай случайный процесс. Подтверждённую правку существующего процесса нового поколения веди по его правилам. [Пример границы](WORKFLOW.md#когда-нужен-процесс).

## Общение с владельцем бизнеса

Собеседник может быть предпринимателем или маркетологом без технической подготовки. Говори на языке его бизнеса: заявка, запись, заказ, письмо, оплата, менеджер. Не выноси технические детали без запроса. При вопросе о готовности назови **один следующий шаг**. Задавай по одному предметному вопросу, максимум три тесно связанных; предлагай варианты и объясняй последствия для клиента. Правила и примеры — [WORKFLOW.md#общение-с-владельцем-бизнеса](WORKFLOW.md#общение-с-владельцем-бизнеса), [method/interview.md](method/interview.md).

Страну работы, часовой пояс отправки и поля формы выясняй у владельца. Не объявляй их значениями «по умолчанию» по валюте, текущему аккаунту или примеру из справки; до ответа оставляй открытым вопросом.

## Начало работы

0. Если нет `.agents/skills/chatium-development/SKILL.md`, выполни
   `chatium get-skills` из корня аккаунта. Проверь зависимость; без неё
   ревью заблокировано. [Установка](build/environment.md#файлы-и-зависимости).
1. Для существующего процесса сначала запусти `node .agents/skills/processes/scripts/context.mjs <process> --no-cards`. Новая процедура применима только при `processEngine: processes-v2`; старые и смешанные процессы веди по [правилам совместимости](build/legacy-processes.md). Не добавляй маркер для обхода проверки.
2. Для нового процесса до записи знаний обнови `origin/main`, создай ветку `process/<process>` именно от него и запусти `scaffold`. Каркас сверит ветку и копию скилла с опубликованным `main`; общая инструкция окружения о публикации в `main` **не разрешает** делать это до согласования запуска. Детали — [WORKFLOW.md#этапы](WORKFLOW.md#этапы).
3. При вопросе о конкретном процессе прочитай актуальную доску через `context` или `board read`; просмотри относящиеся к задаче изображения. Поручение неясного автора в многопользовательском аккаунте требует проверки полномочий. Схема — [build/board.md](build/board.md), [build/board-notes.md](build/board-notes.md).

## Этапы и обязательные ворота

Интервью и материалы → план и карта → независимая проверка архитектуры → согласование владельца «строим так?» → сборка по карточкам → проверка реализации и профильных результатов → тестовый прогон → согласование «запускаем?» → запуск и наблюдение. Согласования фиксируй через `owner-decisions.mjs`, состав и статус заключений — через `reviews.mjs`; [общая процедура](build/commission.md). Статический `kb-check` проверяет структуру, а содержательную достаточность оценивает независимый ревьюер. Принятый план не разрешает боевую отправку.

Перед комиссией закончи пакет этапа. Собери все замечания одной версии, исправь пакетом и повтори лишь затронутые роли по `reviews status`. Не проверяй каждую мелкую правку отдельно; повторный блокер после двух раундов требует выяснить причину. [Порядок](build/commission.md).

После правок: заключения → commit → push ветки → успешная сборка → `check.mjs <process>` (`--task-stage design --knowledge-stage design` на этапе проекта). Хук Start обновляет снимок затронутого процесса для ветки и SHA через несколько секунд после сборки. Обычный `check` только читает карту и проверяет готовность. `--publish-snapshot` нужен лишь для восстановления после разбора сбоя хука. `--no-snapshot` и `context --offline` не подтверждают готовность. Перед запуском нужны ответ владельца, зелёные проверки и тестовый путь. В `main` и боевые автоматизации переходи только после разрешения на запуск.

Отправки до запуска веди только на тестовые контакты с `config.mailings.testOnly: true`. Таблицы живые и в ветке; изменение заполненной схемы требует отдельной проверки и решения. Не записывай файлы процесса через SDK во время его работы. Не меняй файлы скилла внутри клиентского аккаунта. [Остальные правила](WORKFLOW.md#жёсткие-правила).
