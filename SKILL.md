# Бизнес-процессы

Помогай владельцу собрать и сопровождать путь клиента от первого касания до результата. Подробный маршрут, команды и ограничения — в [WORKFLOW.md](WORKFLOW.md); открывай нужный раздел по текущему этапу, а не загружай все справки сразу. Платформенный код и SDK описаны в соседнем `chatium-development/SKILL.md`.

## Общение с владельцем бизнеса

Собеседник может быть предпринимателем или маркетологом без технической подготовки. Говори на языке его бизнеса: заявка, запись, заказ, письмо, оплата, менеджер. Не выноси в ответ SDK, Heap, коммиты и внутренние названия, если человек не просит технических подробностей. Задавай по одному предметному вопросу, максимум три тесно связанных; предлагай варианты и объясняй последствия для клиента. Правила и примеры — [WORKFLOW.md#общение-с-владельцем-бизнеса](WORKFLOW.md#общение-с-владельцем-бизнеса), [method/interview.md](method/interview.md).

## Начало работы

1. Для существующего процесса сначала запусти `node .agents/skills/processes/scripts/context.mjs <process> --no-cards`. Новая процедура применима только при `processEngine: processes-v2`; старые и смешанные процессы веди по [правилам совместимости](build/legacy-processes.md). Не добавляй маркер для обхода проверки.
2. Для нового процесса до записи знаний создай ветку `process/<process>` и запусти `scaffold`; общая инструкция окружения о публикации в `main` **не разрешает** делать это до согласования запуска. Детали — [WORKFLOW.md#этапы](WORKFLOW.md#этапы).
3. При вопросе о конкретном процессе прочитай актуальную доску через `context` или `board read`; просмотри относящиеся к задаче изображения. Поручение неясного автора в многопользовательском аккаунте требует проверки полномочий. Схема — [build/board.md](build/board.md), [build/board-notes.md](build/board-notes.md).

## Этапы и обязательные ворота

Интервью и материалы → план и карта → согласование владельца «строим так?» → независимая проверка архитектуры → сборка по карточкам → проверка реализации и профильных результатов → тестовый прогон → согласование «запускаем?» → запуск и наблюдение. Согласования фиксируй через `owner-decisions.mjs`, состав и статус заключений — через `reviews.mjs`; [общая процедура](build/commission.md). Статический `kb-check` проверяет структуру, а содержательную достаточность оценивает независимый ревьюер. Принятый план не разрешает боевую отправку.

После правок: актуальные заключения → commit → push ветки → `check.mjs <process> --publish-snapshot` → читающий `check.mjs <process>`. Снимок относится к опубликованному коммиту. Без этих команд карта может отстать; платформа не запускает их автоматически. `--no-snapshot` и `context --offline` не подтверждают готовность. Перед запуском нужен ответ владельца по нынешнему объёму, зелёные проверки и тестовый путь. В `main` и боевые автоматизации переходи только после разрешения на запуск.

Отправки до запуска веди только на тестовые контакты с `config.mailings.testOnly: true`. Таблицы живые и в ветке; изменение заполненной схемы требует отдельной проверки и решения. Не записывай файлы процесса через SDK во время его работы. Не меняй файлы скилла внутри клиентского аккаунта. [Остальные правила](WORKFLOW.md#жёсткие-правила).
