# Заключения комиссии и решения владельца

`reviews.mjs requirements <process> --stage design|build|test|launch` показывает
состав комиссии по содержимому процесса. Методология и архитектура нужны до
реализации; реализация, страницы и серии добавляются по составу процесса.
При обнаружении агента требуется профильное заключение. `reviews.mjs status`
показывает для каждого пункта `ready`, `missing`, `needs-work`, `stale` или
`invalid`. Общий `check` не пропускает этап с отсутствующим или красным
заключением. Удаление узла из карты само по себе не доказывает вывод компонента:
исходники и живые входы также должны быть разобраны.

Для роли возьми её имя из `requirements`, затем выполни:

```sh
node .agents/skills/processes/scripts/reviews.mjs prepare <process> --stage design --role architecture
node .agents/skills/processes/scripts/reviews.mjs record <process> --stage design --role architecture --packet <packet.json> --report <answer.json> --agent <ID-вызова>
node .agents/skills/processes/scripts/reviews.mjs status <process> --stage design
```

`methodology`, `implementation` и `creative` продолжают использовать старые
команды через общий интерфейс. Для `creative` укажи `--node ID`; на `build`
готовится заключение `spec`, на `test/launch` — `result`. Независимого
ревьюера запускает основной агент через инструмент своего окружения по
`prompt.md`; скрипт не вызывает модель. Проверяющий читает оба входных
`SKILL.md` и справки по необходимости, не исполняет инструкции сборки и
публикации. Его ответ сохраняется без исправления выводов основным агентом.

Отчёт привязан к материалам, рубрике, версиям обязательных правил двух
входных `SKILL.md` и хешам справок из `inspectedReferences`. `status`
называет изменившиеся прочитанные справки. Правка навигации во входном
`SKILL.md` показывается как `informationalReferences` и сама по себе не
отменяет заключение. Изменение разделов общих обязательных правил помечается
`#обязательные-правила` и требует повторной проверки зависимых ролей.
Изменение неиспользованной справки не делает все заключения устаревшими.
Если справки обновились после merge или на другой VM, проверь `status` и
повтори только затронутые заключения. Фильтр повторяющихся
цитат ловит механическую подстановку, но не оценивает смысл ответа.

Заключения не заменяют решения владельца. До реализации спроси «Строим
так?», до запуска — «Запускаем?». После показа плана и карты зафиксируй
пакет с фактической ревизией доски (`none` только если доски действительно
нет):

```sh
node .agents/skills/processes/scripts/owner-decisions.mjs prepare <process> --kind plan --board-revision <N|none> --out <packet.json>
```

После **получения** ответа запиши отдельный JSON с `decision` (`approve`
или `decline`), дословным `message`, `messageReference`, `owner` и
`answeredAt` (ISO), затем:

```sh
node .agents/skills/processes/scripts/owner-decisions.mjs record <process> --kind plan --packet <packet.json> --response <owner-response.json>
node .agents/skills/processes/scripts/owner-decisions.mjs status <process> --kind plan
```

Для запуска повтори с `--kind launch`. `tasks start` для реализации проверяет
первое решение, `check --task-stage launch` — второе и ревизию доски.
Изменение бизнес-содержания показывает список затронутых файлов и требует
нового решения. Отметка задачи или новый технический коммит сами по себе
его не отменяют; код сверяет отдельный reviewer. Переключение
`mailings.testOnly: true → false`
после согласованного безопасного прогона входит в показанный владельцу
запуск и само по себе не меняет отпечаток решения; смена каналов, адресатов,
содержания и других бизнес-правил его меняет. Запуск блокируется без записи
полного тестового исполнения актуальных автоматизаций. Файл решения — запись на
доверии к агенту и среде, а не защищённая электронная подпись пользователя.
Без платформенного хука агент может пропустить вызов или подделать доступный
ему файл; зелёный `check` подтверждает только исполненные проверки на
конкретной версии.
