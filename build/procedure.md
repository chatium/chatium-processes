# Процедура: от плана до запуска

## 0. Позиция

```sh
node .agents/skills/processes/scripts/context.mjs <process>
```

Продолжай с того этапа, что показал скрипт. Не начинай заново то, что уже
есть в артефактах. Прочитай всю доступную доску и открой относящиеся к задаче изображения
по [board.md](board.md). Учёт поручений — [board-notes.md](board-notes.md);
выполненное повторно не выполняй. Просьба в диалоге не требует отметки на стикере.
`context` также
сверяет сохранённую карту без записи; ошибка чтения — не подтверждение её
актуальности. До первого push/без сети можно `--offline`.
Проверь также показанные `context` структуру знаний и независимое ревью.
Отсутствующий/устаревший отчёт не означает, что надо повторить всё интервью:
подготовь пакет и проверь по [процедуре ревью](../method/review.md).
Настройка SDK и разбор результатов — [map-freshness.md](map-freshness.md).

## 1. Каркас

```sh
git switch -c process/<process>          # или git switch process/<process>
node .agents/skills/processes/scripts/scaffold.mjs <process> --title "Название" --account-id <id>
```

`scaffold` не перезаписывает существующие файлы. Числовой id аккаунта для
`--account-id` — `chatium exec` со строкой `return ctx.account.id` (нужен
хотя бы один коммит со сборкой).

## 2. План и согласование 1

1. После интервью выполни `kb-check`, затем независимый аудит `design`.
   При блокерах уточни знания; независимую разрешённую работу продолжать можно.
2. Заполни `PLAN.md` и `process.yaml` по базе знаний
   ([plan-md.md](../formats/plan-md.md), [process-yaml.md](../formats/process-yaml.md)).
3. Commit/push ветки и `check`: сохрани снимок и открой карту в превью
   по [preview.md](preview.md). Красные проверки на этом шаге нормальны:
   ничего не построено; успешное контрольное чтение снимка всё же обязательно.
4. Покажи план человеческим языком: что получит клиент, из чего процесс,
   что нужно от владельца. Спроси кнопками: «Строим так?» / «Поправить».
5. После «да» — строка `План: согласован <дата>` в `PLAN.md`. Если разрешение
   на этот объём уже дано, зафиксируй его без повторного запроса.
6. Независимый аудит `build`: сначала заверши правки плана и карты.
   Блокеры запрещают объявлять готовность и собирать зависящую от них часть.

## 3. Сборка, задача за задачей

Для каждой задачи `PLAN.md`:

1. `context` — прочитай карточки компонентов задачи.
2. Напиши код и письма по карточкам.
3. `git add` + `git commit`, `chatium typecheck` — ноль ошибок.
4. `git push -u origin process/<process>` — ветка собирается, `main` не
   трогается.
5. `check` — задача зелёная в своей части; снимок записан в Start. Для
   проверки до push используйте `--no-snapshot`, после push повторите без него.
   Если завершена автоматизация, открой её конфиг в превью по
   [карточке автоматизации](../blocks/automation.md#показать-в-превью),
   затем вернись к карте процесса при завершении всей работы.
6. Подготовь сценарии smoke и тестовый режим. До независимого ревью
   реализации выполняй только typecheck и изолированные unit-тесты;
   прогон с данными/отправками/jobs/оплатой — на шаге 5 этой процедуры.
7. Не отмечай ещё не проведённый smoke как выполненный. Реестр тестовых
   записей заполняется фактическими id после прогона.
8. Отметь задачу `[x]`, заверши правки `PLAN.md` и реестра тестов.
   Затем снова commit, push и `check`. Во время сборки отчёт знаний
   может стать `stale` от отметок задач; это видно в проверке, а готовность
   всего процесса пока не объявляется.
9. Проверь `N/M`, включая провалы, и актуальность карты для конечного
   коммита (`verified: true`). Владельцу объясни результат по правилам
   [общения](../SKILL.md#общение-с-владельцем-бизнеса): что работает, что
   ещё мешает запуску и соответствует ли карта последним изменениям.
   После этого новые правки требуют повторения цикла. Промежуточный
   снимок шага 5 не заменяет финальную проверку.

Перед сдачей согласованного объёма закончи правки знаний, плана и карты;
если отчёт знаний устарел, повтори аудит `build`. Обязательно выполни
независимое ревью реализации по [review.md](review.md), устрани блокеры
и сохрани актуальный отчёт. Затем commit → push → `check`. Не вызывай
ревьюера после каждой административной отметки задачи:
собери их к этому рубежу. Изменение бизнес-правил требует ревью до сборки
зависящей от них части. Только код/реестр тестов не меняют хеш знаний.

## 4. Нужно от вас

Собери в `PLAN.md` и перескажи: каналы Sender, платёжка, домен, тексты на
утверждение, тестовый контакт. Не делай за владельца то, что требует его
доступа или решения.

## 5. Тестовый прогон

До первого прогона `node .agents/skills/processes/scripts/code-review.mjs status <process>` должен показать `ready`
для текущих исходников; одного зелёного ревью знаний недостаточно.
Ревью не заменяет тесты и не запускает их само. После исправления поведения
повтори ревью реализации и затронутые тесты.

Пройди путь клиента на тестовом контакте: заявка → запись → событие →
письма. Задержки в тестах автоматически не ускоряются — проверяй шаги по
отдельности через `chatium exec`. Фактические id — в `tests/records.ts`, результаты —
в плане. После последних изменений исходников/реестра/плана обнови отчёты
ревью перед финальным commit → push → `check`.

## 6. Согласование 2

`check` зелёный, smoke пройдены; после последних файловых правок снимок
записан и прочитан обратно. Если с тех пор прошло время —
`check <process> --verify-snapshot`. Открой карту в панели. Покажи:

- ссылку на превью ветки и карту;
- что станет боевым: страницы, письма, автоматизации (их включение);
- что останется за владельцем.

Спроси кнопками: «Запускаем?» / «Ещё поправить». После «да» — строка
`Запуск: согласован <дата>` в `PLAN.md` с объёмом разрешённых действий.
Зафиксируй результаты приёмки и закрытие зависимостей; запусти независимое
ревью знаний `launch` и актуализируй ревью реализации после правок плана.
Положительный отчёт не заменяет фактический smoke или согласие.

## 7. Запуск

Только после второго «да»:

1. Актуальные положительные отчёты знаний `launch` и реализации; проверки
   и приёмка пройдены.
   `TEST_ONLY = false` в `tests/records.ts`, коммит. Если менялись знания, план
   или карта — повторный аудит знаний; изменение `TEST_ONLY`/кода требует
   актуального ревью реализации. Затем push ветки и
   `check <process> --knowledge-stage launch` перед публикацией.
2. Merge ветки в `main`, push — публикация.
3. Включение автоматизаций: `enableAutomation` из `@automations/sdk` в
   `chatium exec`, id — `source-file:<путь конфига>`
   ([automation.md](../blocks/automation.md#включение)).
4. Заверши правки реестра/плана; при изменении плана/карты повтори ревью
   знаний `launch` и реализации. При необходимости commit и разрешённый push в `main`; затем
   `check <process> --knowledge-stage launch` на `main`. У снимка должен быть именно
   конечный SHA `main`, `verified: true`. Открой в превью карту `branch=main`.
   Отчёт: что запущено, ссылки,
   что за владельцем. После этого файлы не меняй без повторной проверки.

## 8. Изменения после запуска

Новая ветка `process/<process>-<что меняем>` и тот же цикл. Разрешение на
предыдущий запуск не распространяется на новый объём: обнови статус
согласования в плане, сохранив историю, и используй этап ревью `build`. Согласование 2 —
перед каждым merge в `main`.
