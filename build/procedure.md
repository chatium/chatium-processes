# Процедура: от плана до запуска

Эта процедура применяется к процессам нового скилла. Сначала `context`
проверяет поколение; для старого, смешанного или неопределённого формата
используй [legacy-processes.md](legacy-processes.md). Нельзя лечить отсутствие
новых артефактов в старом процессе созданием нового каркаса.

## 0. Позиция

```sh
node .agents/skills/processes/scripts/context.mjs <process>
```

Продолжай с того этапа, что показал скрипт. Не начинай заново то, что уже
есть в артефактах. Прочитай всю доступную доску и открой относящиеся к задаче изображения
по [board.md](board.md). Учёт поручений — [board-notes.md](board-notes.md);
выполненное повторно не выполняй. Просьба в диалоге не требует отметки на стикере.
`context` также
сверяет сохранённую карту без записи; ошибка чтения — не подтверждение её
актуальности. До первого push/без сети можно `--offline`.
Проверь также показанные `context` структуру знаний и независимое ревью.
Отсутствующий/устаревший отчёт не означает, что надо повторить всё интервью:
подготовь пакет и проверь по [процедуре ревью](../method/review.md).
Настройка SDK и разбор результатов — [map-freshness.md](map-freshness.md).

## 1. Каркас

```sh
git fetch origin main
git switch -c process/<process> origin/main
node .agents/skills/processes/scripts/scaffold.mjs <process> --title "Название" --account-id <id>
```

`scaffold` не перезаписывает существующие файлы. Числовой id аккаунта для
`--account-id` — `chatium exec` со строкой `return ctx.account.id` (нужен
хотя бы один коммит со сборкой).
При создании нового процесса в Git-аккаунте `scaffold` отвергает `main` и
`master`, ветку без текущего опубликованного `origin/main` и ветку со старой
копией скилла до записи файлов. Флаг `--allow-main` существует только для
тестового аккаунта, где владелец явно разрешил работу прямо в основной
ветке; обычный процесс его не использует. `--dry-run` доступен для просмотра
каркаса без записи.

## 2. План и согласование 1

1. После интервью выполни `kb-check` для структуры знаний. Содержательное
   ревью проводи на общей зафиксированной версии знаний, плана и карты вместе
   с архитектурным заключением, а не отдельным ранним раундом.
2. Заполни `PLAN.md` и `process.yaml` по базе знаний
   ([plan-md.md](../formats/plan-md.md), [process-yaml.md](../formats/process-yaml.md)).
   Для нового процесса добавь рабочие карточки и критерии через
   [процедуру задач](tasks-and-creative.md). Для страниц и серий отдельно
   поставь задачи профильным специалистам на решения, основному агенту —
   на итоговый `spec.yaml` и последующую реализацию. Основной агент может
   наметить черновик во время аудита знаний, но не заменяет им специалистов.
   Создай карточки одним пакетом через `tasks.mjs create-batch`, затем проверь
   `tasks.mjs status <process> --stage design` и исправь разорванные связи
   задач до ревью. Будущие незавершённые задачи допустимы как предупреждения;
   отсутствующий создатель `spec.yaml` — ошибка проекта.
   Если владелец делегировал решения для тестового процесса, до ревью заполни
   `mailings.testOnly`, разрешённые тестовые контакты и уже известные
   `config.variables` (в частности, адрес политики для формы) в
   `.workspace.json`;
   закрой уже полученные ответы в `needsInput`. Эти файлы входят в предмет
   ревью: поздняя правка снова сделает заключение устаревшим.
   Перед передачей на ревью проверь каждый блокер `needsInput`: это действительно
   решение или действие владельца, а не работа исполнителя из карточек. Для
   собственной работы добавь карточку и зависимость задач; не блокируй её
   же через `needsInput`.
3. На одной версии материалов получи методологическое и архитектурное
   заключения через [комиссию](commission.md); собери все замечания перед
   одним пакетом правок. Затем запусти локальный
   `check <process> --task-stage design --knowledge-stage design --no-snapshot`.
   Ошибки проекта, карточек или обязательных заключений исправь до вопроса
   «строим так?». Commit/push ветки, дождись успешной сборки и повтори
   читающий `check` без `--no-snapshot`; открой карту в превью
   по [preview.md](preview.md). Предупреждения о будущей сборке допустимы,
   красный проектный этап или неверный снимок — нет.
4. Покажи план человеческим языком: что получит клиент, из чего процесс,
   что нужно от владельца. Спроси кнопками: «Строим так?» / «Поправить».
5. После «да» запиши исходный ответ по [процедуре решений](commission.md),
   затем отметь согласование в `PLAN.md`. Если разрешение на этот объём уже
   дано, сохрани ссылку на реальный ответ без повторного запроса.
6. Независимый аудит `build`: сначала заверши правки плана и карты.
   Блокеры запрещают объявлять готовность и собирать зависящую от них часть.

Карточки этапов `build`, `test` и `launch`, включая предложения специалистов,
запускай только после принятой комиссии `design` и актуального ответа
«строим так?». Пока ревью проектирования идёт, можно подготовить черновые
вопросы, но не вызывай `tasks start` и не запускай специалистов по этим
карточкам: изменение входов вынудит повторить их работу.

## 3. Сборка связанными группами задач

Разделяй доказательства сборки и тестового исполнения. У карточки `build`
критерии приёмки должны подтверждаться кодом, typecheck и локальными тестами;
фактический POST, запись в живую таблицу, доставка, оплата и просмотр страницы
относятся к карточке `test`. Иначе зависимая задача не сможет стартовать до
общего прогона всей цепочки. До запуска группы проверь этот разрез в карточках
и исправь его одним пакетом. Заверши взаимосвязанные исходники до приёмки
карточки, чьи результаты они меняют: ранняя приёмка `config.ts` станет
устаревшей после следующей правки этого же файла.

Живой прогон не нужен, чтобы **написать** код. Если для итоговой приёмки нужен
рантайм, оставь соответствующий `test`-критерий открытым, реализуй всю группу,
запусти локальные проверки и испытай связанный путь один раз после её сборки.

Для каждой задачи `PLAN.md`:

1. `context` — прочитай карточки компонентов и рабочие задачи. Для выбранной
   карточки вызови `tasks.mjs context`, затем `start`; прочитай все входы.
   Для страницы/серии сначала дождись принятых профильных предложений,
   сведи их с фактами в `spec.yaml`, затем `creative.mjs compile` и
   независимое ревью `spec`; после этого прочитай актуальный `build.md`
   и его обязательные референсы.
2. Основной агент пишет код страниц, форм, автоматизаций и финальные письма
   по карточкам. Не поручай профильному субагенту реализацию лендинга;
   он консультирует или готовит содержание. Reviewer проверяет отдельно.
3. Запусти `chatium typecheck` без аргумента пути для всего аккаунта и
   изолированные локальные тесты. Исправь ошибки до `git add` + `git commit`;
   выборочная проверка папки может пропустить ошибку.
4. `git push -u origin process/<process>` — ветка собирается, `main` не
   трогается.
5. После успешной сборки запусти `check` — задача зелёная в своей части,
   карта соответствует опубликованному коммиту. Снимок после build обновит
   хук Start; при задержке повтори читающий `check`. До push используй
   `--no-snapshot`.
   Если завершена автоматизация, открой её конфиг в превью по
   [карточке автоматизации](../blocks/automation.md#показать-в-превью),
   затем вернись к карте процесса при завершении всей работы.
6. Подготовь сценарии smoke и тестовый режим. До независимого ревью
   реализации выполняй только typecheck и изолированные unit-тесты;
   прогон с данными/отправками/jobs/оплатой — на шаге 5 этой процедуры.
7. Не отмечай ещё не проведённый smoke как выполненный. Реестр тестовых
   записей заполняется фактическими id после прогона.
8. Запиши результат рабочей задачи через `tasks.mjs record`, подтверди её
   критерии через `accept` только на итоговых файлах группы. Карточку с ещё
   не выполненным тестовым критерием не принимай; перенеси такой критерий в
   тестовую карточку до следующего раунда реализации. Отметь T-задачу `[x]`,
   когда приняты все связанные карточки; заверши правки `PLAN.md` и реестра тестов.
   Затем снова commit, push, дождись сборки и запусти `check`. Учётные отметки
   задач, ссылки на рабочие карточки и строки согласования сами по себе не
   отменяют заключение знаний; изменение смысла плана отменяет.
9. Проверь `N/M`, включая провалы, и актуальность карты для конечного
   коммита (`verified: true`). Владельцу объясни результат по правилам
   [общения](../SKILL.md#общение-с-владельцем-бизнеса): что работает, что
   ещё мешает запуску и соответствует ли карта последним изменениям.
   После этого новые правки требуют повторения цикла. Промежуточный
   снимок шага 5 не заменяет финальную проверку.

Перед сдачей согласованного объёма закончи правки знаний, плана и карты;
если отчёт знаний устарел, повтори аудит `build`. Обязательно выполни
независимое ревью реализации по [review.md](review.md), устрани блокеры
и сохрани актуальный отчёт. Затем commit → push → успешная сборка → `check`. Не вызывай
ревьюера после каждой административной отметки задачи:
собери их к этому рубежу. Изменение бизнес-правил требует ревью до сборки
зависящей от них части. Только код/реестр тестов не меняют хеш знаний.

## 4. Нужно от вас

Собери в `PLAN.md` и перескажи: каналы Sender, платёжка, домен, тексты на
утверждение, тестовый контакт. Не делай за владельца то, что требует его
доступа или решения.

## 5. Тестовый прогон

До первого прогона `node .agents/skills/processes/scripts/code-review.mjs status <process>` должен показать `ready`
для текущих исходников; одного зелёного ревью знаний недостаточно.
Для страниц и серий нужны ревью результата и `check --task-stage test`.
Ревью не заменяет тесты и не запускает их само. После исправления поведения
после пакета исправлений повтори затронутые тесты и только те заключения,
которые `reviews status` считает неактуальными или красными.

Сформируй сценарии пути клиента и значимых отказов в `tests/plan.yaml`. Запускай настоящий код выбранной ветки через `test.mjs`, проверяя вход → данные/CRM → событие → автоматизацию → задержку → сообщение → ответ → состояние → остановку. Используй [общие команды и формат](../formats/test-records.md). Не переключай работающий процесс и его исполнения. Визуальные проверки записывай через `record`.

Сначала сверяй рассчитанное время задержки, затем пропускай только ожидание конкретного тестового исполнения. Пропуск не доказывает срабатывание часов спустя несколько дней; отдельное наблюдение таймера нужно при изменении механизма планирования, а не после каждой редакции текста. Прямой запуск не доказывает событийную подписку. Собери исправления и повтори затронутые сценарии пакетом.

Завершённые попытки не перезаписывай. Команда тестирования сохраняет отчёты, артефакты и замечания в Start; проверь обновление доски выбранной ветки без commit/push. `check --task-stage test` оценивает обязательные сценарии, их актуальность и открытые блокеры.
Для новых чувствительных страниц и API отдельно проверь прямое обращение к
опубликованной ветке без входа и под ролями, которым доступ не положен,
включая другого клиента для данных с владельцем. Ожидаемый отказ зафиксируй
в результатах прогона; проверка одной только видимости кнопки не подходит.
Если нужной тестовой роли нет, отметь проверку как неподтверждённую.

## 6. Согласование 2

`check` зелёный, smoke пройдены; после последних файловых правок снимок
записан и прочитан обратно. Если с тех пор прошло время —
`check <process>`. Открой карту в панели. Покажи:

- ссылку на превью ветки и карту;
- что станет боевым: страницы, письма, автоматизации (их включение);
- что останется за владельцем.

Спроси кнопками: «Запускаем?» / «Ещё поправить». После «да» сохрани
решение по [комиссии](commission.md), затем отметь строку
`Запуск: согласован <дата>` в `PLAN.md` с объёмом разрешённых действий.
Зафиксируй результаты приёмки и закрытие зависимостей; запусти независимое
ревью знаний `launch` и актуализируй ревью реализации после правок плана.
Положительный отчёт не заменяет фактический smoke или согласие.

## 7. Запуск

Только после второго «да»:

До публикации зафиксируй [наблюдение, остановку и откат](operations.md),
включая судьбу клиентов посреди серии или оплаты. Покажи владельцу этот
порядок вместе с разрешением на запуск.

1. Актуальные положительные отчёты знаний `launch` и реализации; проверки
   и приёмка пройдены. Оставь `config.mailings.testOnly: true`, автоматизации
   выключенными. После финального commit и push ветки дождись автоматического
   обновления снимка и проверь его через `check`.
2. Merge ветки в `main`, push. Это промежуточная безопасная публикация:
   автоматические цепочки пока выключены, Mailings разрешает только тестовые
   контакты. Проверь опубликованный коммит и состояние обычных подписок: `automations-runtime.mjs <process> --expect disabled`. Сопоставь результаты с новой веткой и значимыми исходниками. История ветки разработки сама не подтверждает `main`: выполни согласованный пакет сценариев в её TestContext. Не включай производственных подписчиков для имитации теста. Отдельно проверь активацию после разрешения владельца.
3. После успешного прогона переключи `config.mailings.testOnly: false`,
   зафиксируй и опубликуй эту настройку. Подтверди, что выбранные каналы,
   получатели и содержание всё ещё соответствуют согласию владельца.
   `check --task-stage launch` требует актуальные обязательные сценарии и отсутствие открытых блокеров. Изменение проверяемых настроек требует повторной оценки затронутых сценариев. Затем включай автоматизации: сначала `getAutomationByPath(ctx, path, 'main')`,
   затем `enableAutomation(ctx, automationId)` из `@automations/sdk` в
   `chatium exec`; проверь `{ success: true }`, при `{ success: false, reason }`
   остановись и разберись с причиной. Не составляй ID из пути
   ([automation.md](../blocks/automation.md#включение)). После всех включений
   одним читающим вызовом проверь фактические подписки:
   `node .agents/skills/processes/scripts/automations-runtime.mjs <process> --expect enabled`.
   Ошибка или неподтверждённый коммит оставляют запуск незавершённым.
4. Заверши правки реестра/плана; при изменении плана/карты повтори ревью
   знаний `launch` и реализации. При необходимости commit и разрешённый push в `main`; затем
   `check <process> --knowledge-stage launch --task-stage launch`
   на `main` после успешной сборки. У снимка должен быть именно
   конечный SHA `main`, `verified: true`. Открой в превью карту `branch=main`.
   Отчёт: что запущено, ссылки,
   что за владельцем. После этого файлы не меняй без повторной проверки.

## 8. Изменения после запуска

Новая ветка `process/<process>-<что меняем>` и тот же цикл. Разрешение на
предыдущий запуск не распространяется на новый объём: обнови статус
согласования в плане, сохранив историю, и используй этап ревью `build`. Согласование 2 —
перед каждым merge в `main`.
Перед изменением используй [порядок сопровождения](operations.md): проверь
живые входы, подписки, данные и клиентов на старом пути. После публикации
наблюдай фактические исполнения и при достижении порога ошибки останови поток.
