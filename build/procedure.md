# Процедура: от плана до запуска

## 0. Позиция

```sh
node .agents/skills/processes/scripts/context.mjs <process>
```

Продолжай с того этапа, что показал скрипт. Не начинай заново то, что уже
есть в артефактах. Прочитай открытые агенту заметки доски. `context` также
сверяет сохранённую карту без записи; ошибка чтения — не подтверждение её
актуальности. До первого push/без сети можно `--offline`.
Настройка SDK и разбор результатов — [map-freshness.md](map-freshness.md).

## 1. Каркас

```sh
git switch -c process/<process>          # или git switch process/<process>
node .agents/skills/processes/scripts/scaffold.mjs <process> --title "Название" --account-id <id>
```

`scaffold` не перезаписывает существующие файлы. Числовой id аккаунта для
`--account-id` — `chatium exec` со строкой `return ctx.account.id` (нужен
хотя бы один коммит со сборкой).

## 2. План и согласование 1

1. Заполни `PLAN.md` и `process.yaml` по базе знаний
   ([plan-md.md](../formats/plan-md.md), [process-yaml.md](../formats/process-yaml.md)).
2. `check` на этом шаге красный — это нормально: ничего не построено.
3. Покажи план человеческим языком: что получит клиент, из чего процесс,
   что нужно от владельца. Спроси кнопками: «Строим так?» / «Поправить».
4. После «да» — строка `План: согласован <дата>` в `PLAN.md`.

## 3. Сборка, задача за задачей

Для каждой задачи `PLAN.md`:

1. `context` — прочитай карточки кубиков задачи.
2. Напиши код и письма по карточкам.
3. `git add` + `git commit`, `chatium typecheck` — ноль ошибок.
4. `git push -u origin process/<process>` — ветка собирается, `main` не
   трогается.
5. `check` — задача зелёная в своей части; снимок записан в Start. Для
   проверки до push используйте `--no-snapshot`, после push повторите без него.
6. Smoke по карточке: страница — в браузере по адресу ветки
   (`?__chtmPreviewMode__=account:process/<process>`); форма и письмо —
   через `chatium exec` на тестовом контакте. `chatium exec` работает на
   сборке закоммиченного `HEAD`: сначала коммит и push.
7. Id тестовых записей — в `tests/records.ts`.
8. Отметь задачу `[x]`, заверши правки `PLAN.md` и реестра тестов.
   Если после шага 5 менялись файлы — снова commit, push и `check`.
9. Перескажи итог (`N/M`) и подтверждение актуальности карты для конечного
   коммита (`verified: true`). После этого новые правки требуют повторения
   цикла. Промежуточный снимок шага 5 не заменяет финальную проверку.

## 4. Нужно от вас

Собери в `PLAN.md` и перескажи: каналы Sender, платёжка, домен, тексты на
утверждение, тестовый контакт. Не делай за владельца то, что требует его
доступа или решения.

## 5. Тестовый прогон

Пройди путь клиента на тестовом контакте: заявка → запись → событие →
письма. Задержки в тестах пока не ускоряются — проверяй шаги по
отдельности через `chatium exec`.

## 6. Согласование 2

`check` зелёный, smoke пройдены; после последних файловых правок снимок
записан и прочитан обратно. Если с тех пор прошло время —
`check <process> --verify-snapshot`. Покажи:

- ссылку на превью ветки и карту;
- что станет боевым: страницы, письма, автоматизации (их включение);
- что останется за владельцем.

Спроси кнопками: «Запускаем?» / «Ещё поправить». После «да» — строка
`Запуск: согласован <дата>` в `PLAN.md`.

## 7. Запуск

Только после второго «да»:

1. `TEST_ONLY = false` в `tests/records.ts`, коммит.
2. Merge ветки в `main`, push — публикация.
3. Включение автоматизаций: `enableAutomation` из `@automations/sdk` в
   `chatium exec`, id — `source-file:<путь конфига>`
   ([automation.md](../blocks/automation.md#включение)).
4. Заверши правки реестра/плана, при необходимости commit и разрешённый
   push в `main`; затем `check` на `main`. У снимка должен быть именно
   конечный SHA `main`, `verified: true`. Отчёт: что запущено, ссылки,
   что за владельцем. После этого файлы не меняй без повторной проверки.

## 8. Изменения после запуска

Новая ветка `process/<process>-<что меняем>` и тот же цикл. Согласование 2 —
перед каждым merge в `main`.
