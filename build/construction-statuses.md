# Состояние сборки на доске

У блока ровно пять состояний. Их рассчитывает Start из фактов; команды
`set-status` нет. Агент не подменяет приёмку собственной меткой «готово».

| Метка | Основание | Как меняется |
|---|---|---|
| В плане (`planned`) | Нет реализации и начатых задач сборки | Создать и начать связанную рабочую задачу |
| В работе (`in-progress`) | Работа начата; результат не принят, доказательства устарели либо недоступны | Завершить задачи, устранить причины, опубликовать актуальную приёмку |
| Собрано (`built`) | Реализация существует, все связанные задачи и зависимости приняты; проверки кода, типов, ревью и согласование проекта актуальны | Правка существенного входа снимает приёмку; повторить затронутую работу и проверку |
| Нужно от вас (`needs-input`) | Задача сборки ожидает ответа либо в `needsInput` есть зависимость, блокирующая design/build | Получить ответ, записать его и возобновить задачу; снять выполненную зависимость |
| Ошибка (`error`) | Связанная задача завершилась ошибкой либо проверка результата этого блока содержит блокирующий дефект | Исправить, возобновить задачу и пройти приёмку |

Приоритет: ошибка блока → зависимость от владельца → принятая сборка →
незавершённая работа → ещё не начато. Общий дефект процесса показан среди
общих условий приёмки. По подстроке пути в сообщении об ошибке принадлежность
блоку не угадывается. Причина и задачи доступны в карточке.

«В работе» означает незавершённую работу, а не то, что агент сейчас печатает.
Неизвестное состояние читается как неподтверждённая сборка, никогда как успех.
Отменённая карточка не исполняет требование: для реализации нужна действующая
задача с результатом. Несвязанный исходник не получает зелёный статус.

У существующего процесса отсутствие квитанций не требует пересобирать бизнес заново. Свяжи текущие исходники и сущности с задачами и критериями, проверь фактический результат, получи актуальные ревью и зарегистрируй приёмку. Не создавай дубликаты таблиц, автоматизаций и рассылок ради статуса.

## Три независимых слоя

**Сборка** подтверждает реализацию. **Тестирование** подтверждает сохранённые
попытки сценариев: покрытие блока/связи — не проверено, частично, успешно,
ошибка, заблокировано, устарело. Попытка дополнительно может выполняться или
быть неполной; её нельзя выдавать за успешную. **Допуск к запуску** требует
проверок launch и отдельного решения владельца. «Собрано» не означает, что
процесс запущен, сообщения получены или тесты прошли.

Транспорт/боевой контакт в `needsInput` с `blocks: [launch]` не блокирует
сборку. До подключения используй внутренний транспорт Sender. Не превращай
условия запуска в фиктивные ошибки сборки и не снимай защиту запуска.

## Обязательный flow агента

1. Свяжи задачи design/build с блоками: `targetNode` и фактические
   `expectedOutputs`. Укажи критерии плана, входы, зависимости и проверяемый
   результат. Не добавляй фиктивные карточки только ради цвета.
2. **До правки принятого результата** открой заново соответствующую задачу.
   Используй `tasks.mjs start/ask/resolve/fail/record/accept/reopen` по смыслу.
   Эти команды сохраняют задачу, затем отправляют прогресс в выбранную ветку
   доски. Каркас этой ветки должен быть опубликован заранее.
3. Читай `boardSync` в ответе каждой изменяющей команды. `pending` означает:
   файл сохранён, обновление доски не подтверждено. Повтори только
   `construction.mjs sync <process>`, а не создание/приёмку задачи.
   При конфликте сначала прочитай состояние, не переигрывай операцию вслепую.
4. Незавершённая работа видна без push с отметкой «Неопубликованная работа».
   Её нельзя превратить в «Собрано». После публикации соответствующей версии
   карточки рабочая отметка погашается; нужна актуальная приёмка исходников.
5. Заверши результат, получи требуемые ревью и прими задачи через штатную
   `tasks.mjs accept`. Затем commit → push своей ветки → успешная сборка →
   `check.mjs <process> --typecheck --task-stage build --knowledge-stage build --publish-snapshot`.
   Для test/launch укажи соответствующие этапы. Запись отчёта допустима и с
   замечаниями: они должны быть видны на доске.
6. Сверь `construction.mjs status <process>`: статус, причину, задачи, общие
   условия, исходную версию приёмки. Открой доску при групповой сдаче.
   Одного кода возврата локального скрипта или `snapshot.verified` недостаточно:
   последнее подтверждает актуальность карты, а не зелёную приёмку.

`construction.mjs sync` также сверяет отменённую локальную работу: только
чистая рабочая копия может убрать собственную неопубликованную отметку,
которая больше не соответствует её файлам. Чужие workspace не затрагиваются.
Прогресс не исчезает по таймеру или от очередной сборки. При сетевой ошибке
он остаётся неподтверждённым с объяснением.

## Версии и доказательства

Снимок содержит `build` (контракт, версия/время проверки, входы с SHA-256,
инвентарь исходников и общие условия) и `nodes[].build` (наличие реализации,
задачи, результаты их приёмки, локальные условия и зависимости от владельца).
`nodes[].progress` — серверные квитанции неопубликованных задач.

Одинаковый расчёт состояний применяется в скилле и Source Build. Хук видит
опубликованные файлы/задачи, но не исполняет независимые проверки и не выдаёт
наличие файлов за приёмку. При неизменных проверенных входах он сохраняет
прежнюю приёмку с **её исходной версией**. При изменении входов или состава
исходников приёмка устаревает. Новый несвязанный отчёт/заметка не инвалидирует
сборку; изменение самого проверенного отчёта или критериев — инвалидирует.
При другом контракте скилла прежние доказательства требуют новой проверки.
Полные серверные логи не входят в снимок.

Если новый commit аккаунта не собирается, `chatium exec` на нём недоступен.
Сохрани ошибку задачи и отправь только её метаданные через существующий
исправный checkout **того же аккаунта**:
`construction.mjs sync <process> --root WORKING_CHECKOUT --exec-root HEALTHY_CHECKOUT`.
Оба origin должны совпадать; SDK checkout должен быть чистым и иметь успешную
сборку своего HEAD. Никаких переключений или правок в нём команда не делает.
Целевая ветка и задачи берутся из `--root`, CAS — из её опубликованного снимка.
Опубликованный commit должен быть предком рабочей версии; расхождение веток
блокирует запись. Код непостроенной версии не выполняется и не считается
проверенным. Это не выбор другой версии SDK: новый экспорт Start всё равно
должен быть опубликован штатно. Без исправного checkout остаётся `pending`;
после восстановления повтори sync, не операцию задачи.
