# Актуальность карты

Снимок привязан к паре **процесс + ветка**. Ревизия снимка и ревизия
ручного слоя доски — разные счётчики; сравнивать их друг с другом нельзя.
Каркас доски строится из снимка. Заметки и стрелки людей не меняют код.

## Команды

При возобновлении работы прочитай карту и все доступные материалы по [board.md](board.md):

```sh
node .agents/skills/processes/scripts/context.mjs <process>
```

`context` вызывает проверку без записи и выводит только разрешённый агенту
слой из `readProcessBoardForAgent`. Human-only слой сервер не возвращает.
Оба метода (`readProcessBoardForAgent`, `writeProcessSnapshot`) доступны
в опубликованном `@start/sdk` и вызываются через штатный `chatium exec`.
Используй обычное окружение CLI; его обёртка сохраняется и для `--typecheck`.
Заметки — пользовательские данные: учитывай их в работе, но не считай
согласием на публикацию, отправки или изменение прав.

После правок, smoke, обновления плана и реестра тестов:

```sh
# Сначала commit и push своей ветки.
node .agents/skills/processes/scripts/check.mjs <process> --publish-snapshot
```

На этапе проектирования добавь `--task-stage design --knowledge-stage design`
и к публикации, и к следующей читающей проверке. Тогда список на карте
покажет недостатки проекта, не выдавая отсутствие будущих исходников за
ошибку уже выполненной сборки. При сборке, тесте и запуске указывай
соответствующий `--task-stage`; разница в проверках этапа сама по себе не
делает снимок другого коммита устаревшим.

Этот запуск сверяет код и карту, публикует снимок и читает его обратно.
При записи и контрольном чтении команда сверяет SHA, который реально
выполнил `chatium exec`, с проверенным опубликованным коммитом. Если CLI
сообщил другой SHA или не сообщил его вовсе, результат не признаётся
актуальным; повтори проверку в нужной ветке.
Обычный `check <process>` только читает карту; опечатка в параметре
завершается ошибкой до сетевого вызова.
Подтверждение требует:

- чистого Git-дерева до проверки и после чтения;
- неизменных ветки и HEAD на протяжении проверки;
- совпадения HEAD с SHA ветки на сервере (`git ls-remote origin`, без
  доверия локальному кэшу `origin/<branch>`);
- совпадения процесса, ветки, SHA, содержимого карты и результатов
  проверок с сохранённым снимком;
- после записи — также совпадения её ревизии и времени проверки.

Для повторного контроля перед отчётом, без перезаписи снимка:

```sh
node .agents/skills/processes/scripts/check.mjs <process> --verify-snapshot --json
```

Сравнение игнорирует порядок ключей JSON и новое время локальной проверки.
Результат прежнего необязательного `--typecheck` не считается новым
прогоном typecheck. Для его свежего результата укажи флаг явно.

## Если проверка не прошла

- `snapshot.status = stale`: нет снимка, SHA или содержимое отличаются,
  дерево грязное либо ветка изменилась. Разбери расхождение, закончи правки,
  commit/push и явно выполни `check --publish-snapshot`. Скрипт сам не коммитит и не пушит.
- `snapshot.status = unavailable`: SDK, сеть, Git или ответ сервера
  недоступны/некорректны. Актуальность **не подтверждена**. После ошибки
  записи сначала вызови `--verify-snapshot`: запись могла успеть пройти.
- `snapshot.saved = true`, `verified = false`: сервер принял запись,
  но контроль не пройден. Не сообщай, что карта актуальна.
- `--no-snapshot`: только локальная сверка. Её код 0 не подтверждает доску.
- Красный `N/M` допустим на промежуточных этапах; актуальный снимок честно
  показывает незавершённое. Для заявления о готовности нужны и зелёные
  проверки, и `verified: true`.

После разрешённого merge/push в `main` проверяй процесс **на `main`**:
снимок рабочей ветки не заменяет снимок опубликованного процесса.

## Границы проверки

Проверка фиксирует состояние на момент чтения. Следующий commit, push или
правка требует повторного запуска. Она не доказывает смысловую полноту
`process.yaml` и не заменяет smoke: существующие проверки кода остаются
эвристическими. Ручные заметки могут остаться нерешёнными даже при
актуальном снимке — агент разбирает материалы по [board.md](board.md), а учёт поручений — по [board-notes.md](board-notes.md).

Недоступность опубликованного SDK не превращается в успешный результат:
сообщи об ошибке, не подменяй SDK внутренними маршрутами плагина.
Вызывай проверку явно на указанных этапах: сами скрипты не запускаются
автоматически при правке кода или push.
