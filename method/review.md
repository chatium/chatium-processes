# Проверка знаний: скрипт и независимый агент

Прочитай этот файл перед первым ревью. Смысловые критерии —
[readiness.md](readiness.md), пул вопросов —
[review-questions.json](review-questions.json). В пуле 26 вопросов; пакет
выбирает только вопросы текущего этапа и предшествующих ему.

## 1. Статическая проверка

```sh
node .agents/skills/processes/scripts/kb-check.mjs <process>
```

Проверяет YAML/frontmatter, статьи, `order`, явные заглушки и локальные
ссылки. Читает раздел процесса, его вложенные статьи и связанные статьи
общей базы; чужой бизнес автоматически в контекст не добавляет. Внешние
ссылки не скачивает. Предупреждение о неопределённой формулировке — повод
прочитать контекст, а не запрет слова. Количество FAQ и болей не нормируется.

Выход 0 — структурных ошибок нет, 1 — найдены ошибки, 2 — запуск не удался.
Зелёный результат не означает, что предложение убедительно, все этапы
описаны и знаний достаточно для сборки.

## 2. Подготовка пакета

```sh
node .agents/skills/processes/scripts/kb-review.mjs prepare <process> --stage build
```

Выбери `design`, `build` или `launch` по цели ревью. Скрипт выдаст пути
`packet.json`, `prompt.md` и снимка библиотеки `library/`, число
файлов/вопросов и `inputDigest`.
Пакет содержит снимки статей, связанные общие материалы, имеющиеся
`PLAN.md`/`process.yaml`, вопросы, инструкцию ревьюера и статические замечания.
Справочники доступны отдельно в библиотеке: их тексты не включены в JSON
пакета и не загружаются в контекст заранее.
После подготовки исходники, пакет и библиотеку не редактируй до окончания
проверки.

На DSH папка пакета создаётся в `/data/external`: `/tmp` там живёт только
одну bash-команду. Локально используется системная временная папка.
Для своего места передай `--out <абсолютный-путь-вне-репозитория>`;
существующий пакет скрипт не перезаписывает. В аккаунт сохраняется только
результат проверки.

Библиотека содержит документацию и шаблоны `chatium-development` и
`processes`, доступные `.d.ts` из `node_modules` и `.typings`. Скрипты скиллов
и JavaScript зависимостей не копируются и не исполняются. `referenceLibrary`
в пакете содержит `version`, общий `digest`, `entrypoints`, `required` и
`files` с путём, размером и SHA-256. Пути заданы относительно `library/`:
`skills/<skill>/…`, `typings/node_modules/…`, `typings/.typings/…`.

Стартовый prompt даёт роль, обязательные вопросы и абсолютные пути двух
входных файлов: `library/skills/chatium-development/SKILL.md` и
`library/skills/processes/SKILL.md`. Методолог читает оба, затем обязательные
`skills/processes/method/README.md` и `skills/processes/method/readiness.md`.
Темы методологии, справки платформы и typings выбирает по проверяемым
вопросам и материалам. Все вопросы пакета обязательны; всю библиотеку читать
заранее не нужно. Инструкции скиллов о сборке, публикации, тестах и вызове
агентов служат критериями проверки, а не поручениями методологу.

Лимиты библиотеки: 2000 файлов, 16 MiB суммарно и 2 MiB на файл; обход
каталогов ограничен. Для большой установки зависимостей можно задать
`referenceTypings` в `<process>/review-scope.json`: список точных путей
`.d.ts` от корня аккаунта заменяет стандартный набор typings. Документация
обоих скиллов всегда входит целиком. Нужные зависимые декларации также
добавляй явно. При превышении лимитов нет тихого урезания; при недостатке
справки/типов reviewer просит основной агент дополнить библиотеку и
подготовить новый пакет. Подробнее о scope — [ревью кода](../build/review.md).

## 3. Вызов независимого субагента

Используй доступный в текущем окружении инструмент создания отдельного
агента без истории основного диалога. Передай содержимое `prompt.md`,
обеспечь чтение пакета и библиотеки, дождись полного ответа. Перед вызовом
сверь аргументы с фактической схемой инструмента.

В окружении DSH:

Прочитай `prompt.md` и передай **его содержимое** штатному инструменту
`subagent` (это вызов инструмента модели, не shell-команда):

```json
{
  "description": "Проверка знаний бизнес-процесса",
  "prompt": "Полный текст prompt.md с путём к packet.json и входным файлам библиотеки",
  "run_in_background": false
}
```

`subagent` создаёт отдельный контекст без переписки родителя. Это даёт
независимый взгляд, а не ограниченный словарь: библиотека доступна для чтения.
`subagent_fork` не подходит для независимого взгляда. Роль задаётся
инструкцией пакета, новый пресет и копия глобального промпта не нужны.
`run_in_background: false` дожидается ответа; не продолжай зависимую
сборку на основании сообщения `started subagent`.

Не передавай выдуманные аргументы `readonly`, `outputSchema` или `persona`:
в публичной схеме этого инструмента их нет. «Только чтение» — инструкция,
не отдельная техническая песочница. При недоступности инструмента сообщи
«независимое ревью не выполнено»; самопроверка не заменяет этот шаг.

В окружении Codex используй `collaboration.spawn_agent` с
`fork_turns: "none"`, если этот инструмент доступен. В других окружениях
выбери эквивалентный вызов с независимым контекстом. Не переноси имена
инструментов и аргументы между окружениями без проверки их схемы.

## 4. Сохранение результата

Субагент возвращает JSON по [reviewer.md](reviewer.md). Сохрани **его ответ**
в файл вне репозитория, не подменяя ответы и выводы. Затем:

```sh
node .agents/skills/processes/scripts/kb-review.mjs record <process> --stage build \
  --packet <путь-к-packet.json> --report <путь-к-ответу.json> \
  --agent <идентификатор-или-ссылка-на-вызов-субагента>
node .agents/skills/processes/scripts/kb-review.mjs status <process> --stage build
```

Скрипт проверяет все ID вопросов, статусы, наличие и точность цитат,
перечень прочитанных файлов и актуальность входов. В `inspectedReferences`
методолог перечисляет реально прочитанные пути библиотеки без повторов,
включая все `referenceLibrary.required`. Цитаты `evidence` берутся из
проверяемых `files`; правило справочника можно ссылать в `reason`.
Валидатор проверяет наличие обязательных путей, но не доказывает чтение.
При `record` сверяются файлы и хеши снимка с манифестом; среди текущих
справок сверяются фактически прочитанные и обязательные.
Пропущенный вопрос,
неверный JSON, чужая цитата или изменённые документы не становятся успехом.
Отчёт — `<process>/reviews/knowledge-<stage>.json`. Выход 0 означает
`ready`, 1 — пробелы/нет актуального отчёта, 2 — ошибку формата или запуска.
Запись отрицательного отчёта допустима и тоже возвращает 1.

Структурные ошибки и пробелы `blocking` блокируют готовность; `advisory`
видны в отчёте и не требуют бесконечной полировки. Нет требования написать
замечание к каждому вопросу. Для неприменимого вопроса нужны обоснование
и свидетельство из материалов, а не пустое «не относится».

Если ответ обрезан/невалиден, один раз запроси исправление формата с тем
же пакетом; при повторной ошибке сообщи об ограничении. Основной агент не
пишет положительный отчёт за проверяющего. Содержательные замечания разбери:
покажи владельцу только вопросы, требующие его решения, по одному следующему
шагу согласно [интервью](interview.md#как-спрашивать); не копируй отчёт или весь
список пробелов в чат. Остальные исправь в разрешённых границах.
После изменений подготовь новый пакет и новый
аудит. Ошибочное замечание не удаляй молча: уточни соответствующее правило
в документах или передай возражение с источниками новому ревьюеру.

## 5. Когда повторять

- `design`: после сбора знаний, перед проектированием плана.
- `build`: после плана и согласования на сборку, до зависимой сборки и
  перед заявлением о её готовности. Перед финальным ревью закончи правки
  статей, `PLAN.md` и карты, включая отметки задач. Не запускай субагента
  ради каждой отметки: промежуточный `stale` виден в `check`, финальная
  готовность требует свежего отчёта. При смене бизнес-правил ревью нужно
  до сборки зависящей от них части.
- `launch`: после документирования приёмки и разрешения на запуск,
  до включения боевых действий. Предварительный аудит до согласования
  честно покажет отсутствие разрешения как блокер.

Изменение входных материалов, критериев, обязательных правил или справок
из `inspectedReferences` делает заключение `stale`; статус называет
затронутые пути. Новая неиспользованная справка сама по себе не отменяет
заключение. Изменение
только кода не требует нового интервью/аудита знаний, но требует отдельного
[ревью реализации](../build/review.md), `check`, затронутых тестов и обновления
снимка карты. Сам отчёт, время и SHA Git
исключены из хеша, поэтому его коммит не создаёт бесконечный цикл.

Финальный `check` сверяет структуру и актуальный отчёт: `build` по умолчанию,
`launch`, если в плане стоит `Запуск: согласован`. Явный выбор:
`--knowledge-stage design|build|launch`; технические проверки не отключаются.
`context` показывает статус ревью, но не запускает модель самостоятельно.

## Ограничения

Валидный отчёт подтверждает структуру ответа и его связь с материалами,
а не истинность экспертного суждения и не подлинность идентификатора вызова.
Реальный запуск обеспечивает агент по обязательной процедуре скилла.
Скрипт не вызывает модель: этот шаг выполняет основной агент. Отдельный контекст
уменьшает зависимость от собственных выводов автора, но модель может
ошибиться; бизнес-решения и разрешения остаются за владельцем.
