# Агенты процесса

Создавай эти файлы только для **принятого** применения ИИ в новом процессе. `agents/spec.yaml` описывает связи и проверяемые требования, а не дублирует бизнес-факты, длинные инструкции или платформенный конфиг. Общие факты — в базе знаний, исполняемые инструкции — в `.agent.json`. Старые процессы автоматически не переводятся на этот формат.

```yaml
# <process>/agents/spec.yaml
version: 1
opportunities:
  - id: lead-help
    need: Помочь человеку выбрать подходящую услугу после заявки
    decision: accepted # accepted | declined | deferred
    reason: Владелец согласовал помощь до разговора с менеджером
agents:
  - key: lead-helper
    config: <process>/agents/lead-helper.agent.json
    node: lead-helper
    opportunity: lead-help
    role: Консультант по заявкам
    outcome: Уточнить потребность и подготовить запись для менеджера
    boundary: Не обещать цену и время без проверки; сложный случай — человеку
    inputs:
      - kind: sender
        source: Канал заявок
    knowledge:
      - .knowledge-base/processes/<process>/offer.md
    tools:
      - name: Проверить доступное время
        source: <process>/agents/tools/availability.ts
    cases: [first-contact, no-slots]
routes:
  - channel: Канал заявок
    firstAgent: lead-helper
    existingConversation: Продолжать цепочку её текущего агента
    fallback: lead-helper
    expectedExistingAgent: lead-helper
    sampleText: Проверка маршрута
handoffs: []
```

`config` и `node` должны совпадать с `source` и `id` узла `kind: agent` в `process.yaml`. `key` — устойчивое имя внутри процесса. После первой публикации получи настоящий `agentId`, запиши его в узел карты и опубликуй изменение; после сборки снимок обновится автоматически, и на карте появится переход к агенту. Каждый сценарий должен быть привязан через `agents[].cases` к своему `cases[].agent`; чужой и неиспользуемый сценарий не засчитываются. `knowledge` перечисляет непустые локальные источники, **доступность в рантайме проверяется отдельно**. `tools` описывает требуемые действия и источники, но регистрация и разрешения тоже проверяются отдельно. `routes` описывает требуемый маршрут, не изменяет настройку канала само по себе. После подключения канала в `channel` запиши его точный Sender ID. Простой публичный SDK задаёт только одного адресата по умолчанию; отдельный запасной агент требует явных правил маршрутизации.

В `.agent.json` лимит токенов, если нужен, задаётся объектом `"tokensLimitPerChain": {"kind":"const","value":6000}`. Число `6000` не проходит схему AI Agents и оставит файл без опубликованного агента.

При передаче добавь в `handoffs[]` поля `from`, `to`, `when`, `summary`, `context`, `onFailure`, `mechanism` и `case`: кому и когда передавать, что сообщить следующему помощнику, какой серверный контекст сохранить, что делать при сбое и каким связанным сценарием это проверять. `case` должен принадлежать исходному помощнику и входить в его `agents[].cases`. Одинаковые `from`/`to`/`when` не дублируй. Если в конфиге есть `goal.type: redirect2`, передача обязана быть описана здесь. Если передач нет, укажи `handoffs: []`.

`mechanism: goal-redirect2` выбирай при достижении проверяемого результата. В исходном `.agent.json` нужна цель `redirect2` с `trigger` и `redirectToAgentIds`; если у целевого агента уже есть опубликованный `agentId` на карте, он должен входить в этот список. Публикуй целевого агента прежде, чем прописывать его ID в цели. Необязательный `goal.messageText` — фиксированный текст: он не подставит факты конкретного клиента, поэтому храни их в CRM/операционной записи. `mechanism: sdk-redirect` выбирай для серверного события или индивидуального резюме и укажи `handler` — существующий файл аккаунта с вызовом публичного `redirectChain`/`redirectChainByContacts`. Скрипт проверяет наличие файла, а независимый reviewer — реальный вызов, права, CRM-контекст и отсутствие петли. Избегай циклов без бизнес-условия выхода.

Для работы без общего канала `routes` может быть пустым; запиши источник входа в `inputs`. Для маршрута в Git храни только `channel`, ожидаемых агентов и правила. Реальные тестовые контакты передай `agents-runtime.mjs` из JSON-файла **вне Git-аккаунта** через `--route-tests FILE`:

```json
{"routes":[{"channel":"Канал заявок","testNewContacts":[{"type":"email","value":"new-test@example.com"}],"testExistingContacts":[{"type":"email","value":"existing-test@example.com"}]}]}
```

Права на файл ограничь владельцем и удали его после проверки. `testNewContacts` — контакты клиента, который есть в CRM, но ещё не имеет цепочки; `testExistingContacts` — **другого** тестового клиента с CRM-цепочкой. Контакты должны быть собственными и нормализованными, как во входе Sender. `expectedExistingAgent` остаётся в `spec.yaml`. `agents-runtime.mjs <process> --route-tests FILE --record` через `dryRunProcessChannelRouting` требует для нового клиента `default-agent`, а для существующего — продолжение цепочки или назначение. Без любого из этих входов результат частичный и не записывается для итогового `check`. Контакты не попадают в сохраняемый файл `tests/agents-runtime.json`; скрипт передаёт их SDK проверки. Не публикуй полный диагностический вывод, если SDK вернул в нём контакт. Для совместимости старые `testNewContacts`/`testExistingContacts` в `spec.yaml` пока читаются, но реальные контакты туда не записывай. SDK не принимает `chainKey`: вход без CRM-ключа, передачу и сохранение контекста проверь контролируемым живым сценарием и приложи наблюдение к ревью помощников. Общий маршрут канала может измениться без коммита: перед финальным запуском повтори `agents-runtime.mjs --record`; проверка запуска принимает результат не старше 15 минут, этап теста — не старше суток. Без платформенного хука это снижает, но не исключает риск последующего изменения маршрута.

Для `inputs: [{kind: manual, ...}]` добавь к агенту `delivery: {kind: direct-output, handler: <process>/tools/captureAnswer.ts}` и реально передай этот `app.function` как `directOutputTool.handler` при ручном `pushMessageToChain`. Допустим и проверенный `delivery.kind: send-tool` с локальным обработчиком, когда ответ должен уходить в согласованный канал. Локальный `check` проверяет существование приёмника; независимое ревью и живой trace подтверждают, что он передан в вызов и ответ принят. Без этого агент может зациклиться на отсутствующем `sendMessageToChat`.

`agents-runtime.mjs` передаёт текущую Git-ветку в `getPublishedAgentVersionBySourcePath`:
SDK читает запись, созданную хуком сборки именно этой ветки, а скрипт сверяет её
отпечаток с локальным файлом и ближайшим `.workspace.json`. `chatium exec`
может исполнять нужный коммит без preview-контекста, поэтому читать через него
«текущий» файл агента другой ветки нельзя. Для этой проверки нужна версия SDK
с методом `getPublishedAgentVersionBySourcePath`.

```yaml
# <process>/agents/cases.yaml
version: 1
cases:
  - id: first-contact
    agent: lead-helper
    situation: Клиент спрашивает о записи после заявки
    expected: Уточняет потребность, проверяет время, предлагает следующий шаг
    evidence: Тестовая запись создана или честно объяснено, почему это невозможно
  - id: no-slots
    agent: lead-helper
    situation: Свободного времени нет
    expected: Не выдумывает время, предлагает согласованный запасной путь
    evidence: Нет ложной записи; передача человеку видна в тестовом состоянии
```

Для реальных действий у каждого сценария заранее опиши тестовые контакты и данные, допустимый эффект, предел ходов/расходов и способ остановки. Реплика «готово» не подтверждает запись или передачу; сравни её с состоянием системы. Не запускай живой тест, пока получатели и инструменты не ограничены тестовым контуром. AI-генерацию рассылок пока не включай в процесс.

Инструмент, читающий или меняющий клиентские данные, должен определить клиента из серверно проверенной цепочки/CRM и отдельно проверить право на нужную запись. `body.input` заполняет модель, поэтому переданный там `customerId`, контакт или ID заказа нельзя считать доказательством принадлежности; `ctx.user` у agent tool отсутствует. Для такого инструмента добавь в `agents/cases.yaml` отрицательный случай с чужой записью и ожидаемым отказом без раскрытия. Публичный каталог без клиентских данных не требует фиктивной CRM-авторизации.

Держи модельный `input` минимальным: цель или бизнес-селектор (например, выбранное занятие), а CRM ID клиента, заявки и технические идентификаторы получай и сверяй на сервере из доверенных контактов и состояния. Когда одно действие использует ответ другого, явно проверь совпадение полей и смыслов: `classId` занятия не становится `leadId` заявки. При нескольких собственных подходящих записях без явного выбора клиента не подставляй «последнюю»; побочное действие требует серверно проверенного свежего выбора либо отказывает, даже если модель взяла действительный селектор из старой истории. Сценарии должны покрывать старую историю без нового поля, чужой и неоднозначный селектор; отказ не создаёт побочный эффект. Это содержательное ревью контрактов, не вывод статического `check`.

Если в `.agent.json` включены `waitingToolEnabled` или `scheduleMessagesEnabled`, добавь к роли в `agents/spec.yaml` план `autonomy`: `mode` (`first-message`, `only_if_no_reply`, `even_if_they_reply` или `repeat_until_cancelled`), `start`, `stateSource`, `stopWhen`, `cancelWhen`, `quietHours`, `maxAttempts` (1–20) и `cancelCase` — ID связанного сценария отмены. Для регулярного продолжения нужен устойчивый `taskKey`. Укажи в конфиге `timeZone` и `tokensLimitPerChain`. Статический `check` проверяет полноту плана, но не доказывает, что агент вызовет `cancelWakeup` и сообщение не уйдёт после отказа; проверь это вместе с другими AI-сценариями в общем безопасном прогоне. Подробности штатного механизма — в `chatium-development/ai-autonomy.md`.
