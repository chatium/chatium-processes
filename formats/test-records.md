# Тестирование и отладка процесса

Проверяй настоящий код процесса скриптами на выделенных данных. Сценарии
применимы к новым и работающим процессам. Ветка изолирует код, но Heap,
каналы и цепочки могут быть общими: изоляцию обеспечивает серверный TestContext.
Не переключай рабочие подписки, testOnly, каналы или исполнения ради теста.

## Сценарии и история

В Git процесса хранятся только план и исполняемые сценарии:

```text
tests/
  plan.yaml
  scenarios/*.mjs
```

Start хранит отдельную запись каждой попытки, разрешённые ресурсы, квитанции
операций, текстовые артефакты и замечания. Результат появляется на доске без
commit, push и сборки. Не создавай файловые smoke-отчёты, records.ts, runs/,
index.json или findings.yaml. Законченная попытка неизменяема; повтор получает
новый runId и previousRunId. Исходные версии не подменяются текущей версией.
Локальный приватный каталог Git содержит только кэш восстановления и токен,
не источник истории. Не добавляй его в публикацию или артефакты.

`plan.yaml` содержит один список сценариев:

```yaml
version: 1
cases:
  - id: welcome
    title: Новая заявка получает приветствие
    kind: runtime
    required: true
    conditions:
      - Новый клиент с разрешённым тестовым адресом
    expected:
      - Канал принял ровно одно сообщение
    targets:
      - kind: node
        id: form
      - kind: link
        id: form-to-welcome
    sources:
      - demo/handlers/submit.ts
      - demo/automations/welcome.automationConfig.json
      - .mailings/storage/processes/demo/welcome.message.yaml
    script: demo/tests/scenarios/welcome.mjs
    capabilities:
      - crm.createCustomer
      - crm.createDeal
      - automations.state
      - automations.skipWait
      - sender.state
    timeoutMs: 300000
```

Пути указываются от корня аккаунта. `sources` — явное замыкание значимых
зависимостей: обработчики, условия, данные настроек, автоматизации, варианты
сообщений, инструкции/настройки ИИ и импортируемые модули процесса. `.workspace.json`
и скрипт включаются автоматически. Объяви все зависимости; одного entrypoint
недостаточно. Изменение условий/критериев, скрипта или зависимости делает
доказательство устаревшим. Отчёт и заметка не меняют актуальность.

Для шага используй `{kind: step, id: <stepId>, source: <automationConfigPath>}`.
ID узлов, связей и шагов должны существовать. Для визуальной проверки укажи
`kind: browser`, не задавай script. Условия и критерии остаются обязательными.

## Запуск

Сначала опубликуй проверяемый код в разрешённую ветку и дождись успешной сборки.
Результаты тестирования публикации не требуют. Команда проверяет исполненный
коммит и соответствие значимых исходников. Смена версии во время исполнения
даёт неполный результат, а не успех новой версии.

```sh
node <scripts>/test.mjs demo run --case welcome --scope /private/demo-scope.json
node <scripts>/test.mjs demo status
node <scripts>/test.mjs demo show --run run-...
node <scripts>/test.mjs demo logs --run run-...
node <scripts>/test.mjs demo cleanup --run run-...
```

Файл scope находится вне репозитория:

```json
{
  "contacts": [{ "type": "email", "value": "selected-test-address@example.test" }],
  "channels": ["selected-channel-id"],
  "variants": { "processes/demo/welcome": "processes/demo/welcome.message.yaml" },
  "plugins": { "start": "codex/process-testing", "automations": "codex/process-testing" }
}
```

`plugins` — необязательный выбор опубликованных веток плагинов; укажи все
модули проверяемого комплекта. Он сохраняется в приватном каталоге Git для
последующих команд. Пустой объект возвращает выбор к опубликованным main.
Команда использует настоящий HTTP-preview Start и штатный перенос текущей
сессии Developer в HTTP-клиент. Данные сессии хранятся только в приватном
каталоге Git, вне отчётов; клиент обновляет их через восемь минут. Подмена
`ctx.env` не применяется.
Сервер фиксирует выбор веток и отпечатки исполняемого кода SDK; изменение
зависимости делает доказательство устаревшим. При разработке самих плагинов
обновляй отпечаток их командой `node scripts/process-testing-version.mjs --write`;
локальная команда без `--write` сверяет его с исходниками.

Это выбранные пользователем или разрешённые тестовым аккаунтом получатели.
Не подставляй произвольные реальные контакты. Сервер проверяет контакты,
каналы, принадлежность ресурсов и исходники на каждом переходе. Клиентский
`test: true` защиты не даёт. Неизвестный или неподдерживаемый безопасный SDK
блокирует сценарий с объяснением. Нельзя обходить блокировку прямой отправкой.

`scenarios/*.mjs` экспортирует `default async function(test)`. Доступны:

- `operation(name, input, requestId)` — операция с обязательным устойчивым ID;
- `attempt(name, input, requestId)` — то же, но возвращает blocked/uncertain для отрицательных проверок;
- `check(criterion, ok, actual)` — проверка критерия из YAML;
- `observe(title, summary)`, `ref(module, kind, id)`, `limitation(text)`;
- `artifact(name, textOrObject, title)` — очищенная выдержка txt/json/md до 256 КиБ;
- `waitFor(read, done, {timeoutMs, intervalMs})` — ограниченное ожидание состояния;
- `contacts`, `channels` — выбранные тестовые ресурсы, не сохраняй их открытым текстом.

`getProcessTestCapabilities` возвращает операции установленных SDK, их
`available` и причину недоступности зависимости. Наличие новой ветки обработчика
не доказывает, что импортируемый SDK уже содержит её экспорты. При несовпадении
версий команда сохраняет blocked до любых действий; не публикуй зависимость
в main в обход согласованного порядка ревью. Операции
с побочными эффектами используют существующий код модулей, отдельного движка
бизнес-логики нет. Повтор requestId с теми же входами возвращает квитанцию,
с другими входами блокируется. При pending/uncertain сначала прочитай состояние
по сохранённым ID; новый requestId не является способом повторить неизвестную
отправку. Прямой запуск автоматизации и запуск тестовым событием — разные сценарии.

В конце команды прогон закрывается, исполнения/цепочки останавливаются,
тестовые записи убираются разрешённым для модуля способом. Доставка уже принятого
сообщения не отменяется, журнал не удаляется. После аварийного завершения агента
выполни cleanup; истечение разрешения блокирует поздние побочные эффекты.
Незавершённая очистка остаётся видна в квитанциях и не считается успешной.

## Наблюдения и границы доказательства

Результат содержит сценарий, входы, критерии/assertions, фактические наблюдения,
версию и SHA исходников, runtime ID, пропущенные ожидания, артефакты, ограничения
и предыдущую попытку. `show` отдельно возвращает платформенные квитанции и
зарегистрированные сервером ресурсы. Оценка агента не превращается в факт
получения сообщения. `logs` заново читает состояние модулей по этим ID.

Статусы попытки: running, passed, failed, blocked, incomplete. Последний означает
неполное доказательство, включая таймаут/неизвестный исход или смену версии;
его нельзя трактовать как отказ действия или успех. Покрытие элемента вычисляется
по связанным сценариям: failed → stale → blocked; все passed дают passed;
без сценариев/попыток — not-tested, смесь остальных — partial. Открытое
блокирующее замечание не позволяет показать успешное покрытие.

Для задержки запиши ожидаемую дату и фактические scheduledFor/статус ожидания.
Совпадение подтверждает расчёт задержки; живое ожидание не требуется. Пропуск
отменяет конкретное задание и продолжает тестовую цепочку. Проверь отсутствие
дубля и остановку дальнейшей серии после целевого события. Проверки дат делай
подготовленными данными; при недоступном управлении конкретным временем расчёта
запиши ограничение вместо искусственного успеха.

Тестовое событие проходит штатный matcher и payloadMapping выбранной версии,
но не вызывает обычных производственных подписчиков. Это подтверждает маршрут
обработчика, не доставку события внешним транспортом. В коде процесса передавай
TestContext во все действия и фоновые переходы; побочные эффекты выполняй через
защищённые SDK. Произвольный HTTP или sandbox-платёж с обычными хуками нельзя
считать изолированным. До поддержки безопасного адаптера такой шаг блокируется.
Логируй runId и ID исполнения/цепочки/отправки без контактов и токенов.

Для ИИ фиксируй доступные сведения о модели/настройках и использованных
инструментах. Проверяй изменения данных и смысл ответа по явной рубрике,
указывай проверяющего и предел оценки. Дословного совпадения не требуй.
Критичные случаи повторяй при существенном изменении модели или инструкций.
Самостоятельные агенты не требуют отдела или агента-координатора.

Различай подготовку сообщения, принятие каналом, ошибку и получение адресатом.
Журнал Sender или запись чата не доказывают фактический inbox. Визуальное
подтверждение владельца можно сохранить отдельным browser-сценарием. Личный
почтовый ящик агента — внешняя ожидаемая возможность: когда появится SDK,
добавим получение, вложения и ответы без изменения формата попыток.
Проверки под чужими пользовательскими ролями в текущий объём не входят.

## Браузер, замечания и доска

Браузер нужен для вёрстки, форм и взаимодействия. Серверную обработку, условия,
переменные, события, сообщения и CRM проверяй скриптами. Для ручной проверки:

```sh
node <scripts>/test.mjs demo record --case layout --evidence /private/layout.json
node <scripts>/test.mjs demo finding --evidence /private/finding.json
```

Evidence содержит assertions, observations, limitations и artifacts.
Для текста артефакт задаётся `{title, file}`; для штатного хранилища —
`{title, storageHash, sha256}`. Не прикладывай HTML как исполняемую страницу.
Finding содержит `{revision, finding}`: id, caseId, title, severity
(blocking/advisory), status (open/resolved), openedIn, resolvedIn и добавляемую
history `{at,note}`. Начальная revision — 0; закрытие ссылается на успешную попытку.
История замечания не переписывается.

Режим «Тестирование» показывает условия, критерии, попытки, замечания и артефакты,
покрытие блоков и связей отдельно от сборки. Фильтры — элемент, сценарий,
результат. Полный отчёт открывается в отдельной вкладке Start; текст не исполняется.
Комментарий/поручение — существующая заметка с ID сценария и попытки. История
читается по выбранной ветке и обновляется без push. Согласование запуска
ссылается на конкретный набор runId и их версии.

`check --task-stage test|launch` читает актуальные результаты из Start и проверяет
обязательные сценарии и блокеры. Локальный кэш не доказывает готовность.


Операция с `pending`/`uncertain` не повторяется с новым ID. Команда `reconcile`
вызывает только чтение исхода у провайдера. Для Sender сохраняется исходный
sendId; если надёжного наблюдения нет, статус остаётся uncertain. Cleanup
идемпотентен и повторяется с прежним requestId после завершения предыдущего
вызова. Состояние `completed` означает завершение операции SDK, результат
бизнес-действия проверяется отдельно.

Опросы `waitFor` не создают квитанций. Завершающее наблюдение сохраняется с
`capture: true` и попадает в runtime refs. Сервер связывает kind, критерии,
цели и весь объявленный список зависимостей с выбранным сценарием плана.
Изменение исходников при финализации делает попытку incomplete.

Возможность провайдера считается доступной только при совместимом реально
импортированном SDK. В версии результата различаются отпечаток адаптера,
протокол и импортированный SDK. Несвязанные файлы интерфейса/другого модуля
не входят в manifest адаптера. Сценарий объявляет capabilities всех зависимых
провайдеров, включая вызываемые из действий и инструментов.

Обработчик кода процесса может участвовать в тесте после явной регистрации
через account hook `@automations/process-test-routes` или
`@agent-process/process-test-tools`: элемент `{protocol: 2, route: handler.toJSON()}`.
Его исходник обязательно входит в sources сценария. Обработчик проверяет
серверный TestContext, принадлежность изменяемых сущностей и получателей;
регистрация сама по себе не делает произвольный внешний эффект безопасным.
Неизвестный или не объявленный обработчик блокируется до его вызова.

История закрытой цепочки ИИ остаётся читаемой; право продолжить исполнение
проверяется отдельно. Redirect разрешён только в закреплённый исходник агента
того же прогона и сохраняет изоляцию, инструменты и тестовый получатель ответа.
Неподдерживаемые native/автономные внешние действия не исполняются. Для grounded
ответов сохраняются штатные инструменты чтения базы знаний и профиля.

Для отдельной диагностики платформы есть `preview`: первый вызов планирует
маленькое задание без сообщений и бизнес-записей; чтение с `--probe ID` показывает,
сохранились ли account/plugin preview и исходники Start. Эта проверка не требует
новых импортов SDK в зависимых плагинах.
